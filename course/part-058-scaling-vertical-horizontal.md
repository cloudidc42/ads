# Part 058: Scaling Strategy — Vertical vs Horizontal Scaling

**Section:** F — Facebook Optimization, Scaling & Budget (Part 056–063, Step 551–630)
**Step ที่ครอบคลุม:** 571–580 (จาก 1000 Steps ทั้งหมด)
**เวลาเรียนโดยประมาณ:** 7–8 ชั่วโมง (อ่าน+ทำความเข้าใจ 3 ชม. / วางแผน Roadmap และฝึกคำนวณ 4–5 ชม.)

หาแคมเปญที่ Win ได้แล้วคือความสำเร็จขั้นที่ 1 แต่การ "Scale" มันให้โตขึ้นโดยไม่พังคือความสำเร็จขั้นที่ 2 ซึ่งยากกว่ามาก — นักยิงแอดมือใหม่จำนวนมากพอเจอแคมเปญที่ผลดี มักรีบเพิ่มงบทันที 2-3 เท่าในวันเดียว แล้วเจอ Cost per Result พุ่งขึ้นทันทีจนต้องถอยกลับมาที่งบเดิม สิ่งที่เกิดขึ้นไม่ใช่เพราะ "โชคไม่ดี" แต่เป็นเพราะการ Scale แบบผิดวิธี — ไปกระตุ้น Learning Phase ให้รีเซ็ต หรือดัน Audience ให้ Saturated เร็วเกินไป

Part นี้จะสอนสองแนวทางหลักของการ Scale: **Vertical Scaling** (เพิ่มงบในสิ่งที่ Win อยู่แล้ว) และ **Horizontal Scaling** (ขยายไปยัง Audience/Placement/Creative ใหม่) พร้อมไทม์ไลน์การเพิ่มงบแบบวันต่อวันที่ใช้งานได้จริง และกรอบการจัดการความเสี่ยงที่ทำให้การ Scale ไม่กลายเป็นหายนะ

ข้อความสำคัญที่ต้องจำไว้ตลอดทั้ง Part นี้คือ **การ Scale ที่ยั่งยืนไม่ใช่การกดปุ่มเพิ่มงบให้เร็วที่สุด แต่คือการสร้างระบบที่ทำซ้ำได้ ปลอดภัย และมีแผนสำรองเสมอ** — นักยิงแอดที่ Scale เก่งจริงๆมักไม่ใช่คนที่ "กล้าเสี่ยงที่สุด" แต่คือคนที่มีวินัยในการทำตามกระบวนการซ้ำๆจนมันกลายเป็นธรรมชาติ

## Step 571: Vertical Scaling — กลไกและ 20% Rule

### นิยาม

Vertical Scaling คือการเพิ่ม **งบประมาณ** ให้กับ Ad Set หรือ Campaign ที่พิสูจน์แล้วว่าทำงานได้ดี (Winner) โดยไม่เปลี่ยนโครงสร้างอื่นเลย — ไม่เปลี่ยน Audience ไม่เปลี่ยนครีเอทีฟ ไม่เปลี่ยน Placement เพียงแค่ "เติมเชื้อไฟ" ให้สิ่งที่ทำงานได้ดีอยู่แล้วทำงานมากขึ้น

### ทำไมต้องมี 20% Rule

ตามที่ทบทวนใน Part 018 การเพิ่มงบเกิน 20% ในครั้งเดียวจะทำให้ Meta พิจารณาว่าเป็น "การเปลี่ยนแปลงที่มีนัยสำคัญ" และมักเข้าสู่สถานะ Learning ใหม่บางส่วน (Learning Limited ชั่วคราว) ทำให้ระบบต้องเสียเวลาสำรวจ Auction ใหม่อีกครั้ง ซึ่งมักทำให้ Cost per Result พุ่งขึ้นชั่วคราวในช่วงนั้น

### กลไกที่แท้จริงเบื้องหลัง 20% Rule

เมื่อคุณเพิ่มงบ ระบบ Machine Learning ของ Meta จะพยายามหา Auction ใหม่ที่มี "Value" สูงพอจะสมกับงบที่เพิ่มขึ้น ถ้าเพิ่มงบทีละน้อย (≤20%) ระบบสามารถขยายวงการประมูลอย่างค่อยเป็นค่อยไปโดยยังใช้ "ความรู้" ที่สั่งสมมาจากงบเดิมได้ต่อเนื่อง แต่ถ้าเพิ่มงบมากในครั้งเดียว (เช่น 100%) ระบบต้องหา Auction ใหม่จำนวนมากอย่างรวดเร็ว ซึ่งมักทำให้เข้าถึงกลุ่มคนที่ "Value" ต่ำกว่าเดิมปนเข้ามาด้วย

### ตัวอย่างตารางขั้นบันไดการเพิ่มงบ (20% Rule)

Ad Set หนึ่งงบเดิม 1,000 บาท/วัน ต้องการ Scale ไปที่ 2,500 บาท/วัน (เพิ่ม 150%):

| รอบที่ | งบก่อนปรับ | เพิ่ม 20% | งบใหม่ | ระยะเวลาที่ควรรอก่อนปรับรอบต่อไป |
|---|---|---|---|---|
| 1 | 1,000 บาท | +200 | 1,200 บาท | 3 วัน |
| 2 | 1,200 บาท | +240 | 1,440 บาท | 3 วัน |
| 3 | 1,440 บาท | +288 | 1,728 บาท | 3 วัน |
| 4 | 1,728 บาท | +346 | 2,074 บาท | 3 วัน |
| 5 | 2,074 บาท | +415 | 2,489 บาท (≈2,500) | เสร็จสิ้น |

รวมเวลาที่ใช้ทั้งหมด: 5 รอบ x 3 วัน = 15 วัน จากงบ 1,000 บาท ไปถึง 2,500 บาท อย่างปลอดภัย เทียบกับการเพิ่มทีเดียว 150% ที่มีความเสี่ยงสูงมากที่ Cost per Result จะพุ่งขึ้นและ Learning Phase รีเซ็ตเต็มรูปแบบ

### เมื่อไหร่ปลอดภัยที่จะปรับงบรอบต่อไป

ไม่ควรยึดติดกับ "จำนวนวัน" อย่างเดียว ควรเช็กเงื่อนไขต่อไปนี้ก่อนปรับรอบใหม่:

1. Ad Set กลับสู่สถานะ Active (ไม่ใช่ Learning) แล้ว
2. Cost per Result กลับมาใกล้เคียงหรือดีกว่าก่อนปรับงบครั้งล่าสุด
3. Frequency ยังไม่พุ่งสูงผิดปกติ
4. ผ่านมาอย่างน้อย 2-3 วันเต็ม (ให้มีข้อมูลสะสมมากพอ)

### ข้อผิดพลาดที่พบบ่อย

- เพิ่มงบ 20% ทุกวันติดกันโดยไม่รอให้ Ad Set กลับสู่ Active ก่อน ทำให้สะสมความไม่นิ่งไปเรื่อยๆ (Learning Limited ต่อเนื่อง)
- ใช้ 20% Rule กับ CBO ที่มี Ad Set ที่มีปัญหาต่างกันอยู่ในนั้น โดยไม่แยกว่า Ad Set ไหนคือตัว "ชนะ" ที่ควรได้งบเพิ่มจริงๆ
- ตกใจเมื่อ Cost per Result ขึ้นเล็กน้อยหลังปรับงบ 1-2 วันแรก ทั้งที่เป็นความผันผวนปกติของ Learning ชั่วคราว ยังไม่ต้องรีบถอยกลับ

## Step 572: Horizontal Scaling — กลไกการขยายไปยัง Audience/Placement/Creative ใหม่

### นิยาม

Horizontal Scaling คือการ **ขยายพื้นที่** ของแคมเปญออกไป ไม่ใช่การเพิ่มงบในที่เดิม แต่เป็นการสร้าง Ad Set ใหม่ (Duplicate) ไปยัง Audience ใหม่, Placement ใหม่, หรือ Creative ใหม่ ในขณะที่ Ad Set ตัวเดิมยังรันต่อเนื่องไปตามปกติไม่ถูกแก้ไข

### สามรูปแบบหลักของ Horizontal Scaling

**1. Audience Expansion** — Duplicate Ad Set ที่ชนะ แล้วเปลี่ยน Audience เป็นกลุ่มใหม่ที่ยังไม่เคยทดสอบ (เช่น จาก Lookalike 1% ไปสร้าง Lookalike 2-5%, หรือจาก Interest A ไปทดสอบ Interest B ที่เกี่ยวข้อง)

**2. Creative Expansion** — คงโครงสร้าง Audience/Budget เดิม แต่เพิ่ม Ad ใหม่เข้าไปในชุดทดสอบ เพื่อลด Ad Fatigue และหา Creative Winner ตัวใหม่มาทดแทนตัวเดิมที่กำลังจะล้า

**3. Placement/Platform Expansion** — ขยายจาก Facebook อย่างเดียวไปยัง Instagram, หรือจาก Feed อย่างเดียวไปยัง Reels/Stories ที่ยังไม่เคยทดสอบเต็มรูปแบบ

### ตัวอย่างการทำ Horizontal Scaling จริง

Ad Set "Lookalike 1% — Purchase" ทำ Cost per Purchase ได้ 120 บาท (ดีมาก) ต้องการ Scale แบบ Horizontal:

| ขั้นตอน | การทำ | ผลที่คาดหวัง |
|---|---|---|
| Duplicate ครั้งที่ 1 | สร้าง Ad Set ใหม่ Audience = Lookalike 2-5% (Audience ใหญ่กว่า) | ขยาย Reach ได้มากขึ้นแม้ CPA อาจสูงกว่าเล็กน้อย |
| Duplicate ครั้งที่ 2 | สร้าง Ad Set ใหม่ Audience = Interest ที่เกี่ยวข้อง (เช่น สนใจแบรนด์คู่แข่ง) | เปิดโอกาสหา Winner Audience ใหม่ที่ไม่ทับซ้อนกับ Lookalike |
| Duplicate ครั้งที่ 3 | Ad Set เดิม (Lookalike 1%) แต่เพิ่ม Creative ใหม่ 3 ตัว | ลด Fatigue ของ Audience เดิม โดยไม่กระทบ Learning ของ Ad Set หลัก |

### ข้อดีของ Horizontal เหนือ Vertical ในบางสถานการณ์

- ไม่มีความเสี่ยงรีเซ็ต Learning Phase ของ Ad Set เดิมเลย เพราะไม่ได้แก้ไขอะไรในนั้น
- เปิดโอกาสค้นพบ Audience/Creative Winner ตัวใหม่ที่อาจดีกว่าตัวเดิม
- กระจายความเสี่ยง ไม่ผูกรายได้ทั้งหมดไว้กับ Ad Set เดียว (เชื่อมโยงกับ Step 578)

### ข้อจำกัดของ Horizontal Scaling

- ต้องใช้เวลาให้ Ad Set ใหม่ผ่าน Learning Phase ของตัวเอง (ไม่ได้ผลทันทีเหมือน Vertical ที่ใช้ประโยชน์จากข้อมูลเดิม)
- ถ้าไม่ระวัง Audience ใหม่กับ Audience เดิมอาจ Overlap กันมาก ทำให้แข่งประมูลกันเอง (Internal Competition) และ CPM สูงขึ้นทั้งสองฝั่ง

### วิธีเช็ก Audience Overlap ก่อนทำ Horizontal Scaling

Meta Business Manager มีเครื่องมือ "Audience Overlap" ในส่วน Audiences ที่ให้เช็กว่า Custom Audience หรือ Lookalike สองกลุ่มมีคนซ้ำกันกี่ % ก่อนตัดสินใจ Duplicate Ad Set ควรเช็กค่านี้เสมอ — ถ้า Overlap สูงกว่า 20-30% มีความเสี่ยงสูงที่ Ad Set ใหม่จะแข่งประมูลกับ Ad Set เดิมเอง (Internal Competition) ทำให้ CPM ของทั้งสองฝั่งสูงขึ้นโดยไม่ได้ประโยชน์เพิ่มจริง

| คู่ Audience ที่เช็ก | % Overlap | คำแนะนำ |
|---|---|---|
| Lookalike 1% vs Lookalike 1-2% | 35% | สูงเกินไป ควรเลือกแค่ตัวเดียวหรือ Exclude กลุ่มที่ซ้ำ |
| Lookalike 1% vs Interest กว้าง (ไม่เกี่ยวกับ Lookalike) | 8% | ปลอดภัย ไม่น่าแข่งกันเองมาก |
| Retargeting Cart 7 วัน vs Retargeting Cart 30 วัน | 60%+ | ซ้ำมากเพราะ 7 วันเป็นส่วนย่อยของ 30 วัน ควร Exclude กลุ่ม 7 วันออกจากกลุ่ม 30 วัน |

### ข้อผิดพลาดที่พบบ่อย

- Duplicate Ad Set ไปยัง Audience ที่ทับซ้อนกับ Audience เดิมมากเกินไป (เช่น Lookalike 1% กับ Lookalike 1-2% ที่มีคนซ้ำกันมาก) ทำให้แข่งกันเองในระบบ Auction
- ทำ Horizontal Scaling ทีเดียวหลาย Ad Set ใหม่พร้อมกัน (10+ กลุ่ม) จนงบกระจายเบาเกินไปแต่ละกลุ่ม ทำให้ไม่มี Ad Set ไหนได้งบพอจะจบ Learning Phase เลย
- ไม่เช็ก Audience Overlap ก่อน Duplicate เลย ทำให้เสียงบไปกับการแข่งประมูลกับตัวเองโดยไม่รู้ตัว

## Step 573: เมื่อไหร่ควรใช้ Vertical เมื่อไหร่ควรใช้ Horizontal

### กรอบการตัดสินใจ

| สัญญาณที่เห็น | แนะนำให้ใช้ | เหตุผล |
|---|---|---|
| Ad Set ชนะ แต่ Audience ยังใหญ่ ยังไม่มีสัญญาณ Saturation | Vertical | ยังมีพื้นที่ให้เพิ่มงบในกลุ่มเดิมได้อีกมาก |
| Ad Set ชนะ แต่ Audience เล็ก (< 500,000 คน) | Horizontal | เพิ่มงบไปมากในกลุ่มเล็กจะ Saturate เร็ว ควรขยายพื้นที่แทน |
| Frequency เริ่มไต่สูง แต่ CPA ยังคงที่ | Horizontal (เพิ่ม Creative ใหม่ก่อน) | ยืดอายุ Ad Set เดิมด้วยการลด Fatigue โดยไม่กระทบ Learning |
| Frequency ยังต่ำ CPA มีเสถียรภาพต่อเนื่อง 7+ วัน | Vertical | สัญญาณบวกครบ พร้อมสำหรับการเพิ่มงบตาม 20% Rule |
| ต้องการทดสอบตลาด/กลุ่มเป้าหมายใหม่ที่ยังไม่เคยลอง | Horizontal | Vertical ไม่ช่วยเรื่องการค้นพบ Audience ใหม่เลย |
| ต้องการเพิ่มรายได้เร็วที่สุดจากสิ่งที่พิสูจน์แล้ว | Vertical | เร็วกว่าเพราะไม่ต้องรอ Learning Phase ใหม่ |

### แนวทาง Hybrid ที่มืออาชีพใช้จริง

ในทางปฏิบัติ นักยิงแอดระดับมืออาชีพจะทำทั้งสองอย่าง **พร้อมกัน** ไม่ใช่เลือกอย่างใดอย่างหนึ่ง — เพิ่มงบ Ad Set หลักตาม 20% Rule (Vertical) ไปพร้อมๆกับสร้าง Ad Set ใหม่ทดสอบ Audience/Creative เพิ่ม (Horizontal) เพื่อให้มี "Winner ตัวใหม่" พร้อมมาทดแทนเมื่อ Ad Set หลักเริ่มถึงจุด Saturation (รายละเอียดเต็มรูปแบบอยู่ใน Step 574)

### ข้อผิดพลาดที่พบบ่อย

- เลือกทำ Vertical อย่างเดียวตลอดจนกว่าจะ Saturate เต็มที่ แล้วค่อยเริ่มคิดหา Audience ใหม่ ทำให้เสียเวลาช่วง Transition ที่รายได้ตกฮวบก่อนหา Winner ใหม่ได้
- เลือกทำ Horizontal อย่างเดียวโดยไม่เคย Scale งบ Ad Set ที่ชนะแล้วเลย ทำให้พลาดโอกาสสร้างรายได้จากสิ่งที่พิสูจน์แล้วว่าดี

## Step 574: Scaling Roadmap แบบผสมสองกลยุทธ์

### แนวคิด "Core-Satellite Scaling Model"

แบ่งโครงสร้างการ Scale เป็น 2 ส่วน:

**Core (แกนหลัก)** — Ad Set ที่พิสูจน์แล้วว่าชนะ ใช้ Vertical Scaling เพิ่มงบตาม 20% Rule ต่อเนื่อง เป็นแหล่งรายได้หลักที่มั่นคง

**Satellite (ดาวเทียม)** — Ad Set ใหม่ที่สร้างขึ้นเพื่อทดสอบ Audience/Creative/Placement ใหม่ๆ (Horizontal) งบน้อยกว่า Core มาก แต่มีเป้าหมายเพื่อ "ค้นหา Core ตัวใหม่" ในอนาคตเมื่อ Core เดิมเริ่ม Saturate

### ตัวอย่างสัดส่วนงบที่แนะนำ

| ระยะ | สัดส่วนงบ Core | สัดส่วนงบ Satellite |
|---|---|---|
| เริ่ม Scale ใหม่ | 70% | 30% |
| Core มีเสถียรภาพดีต่อเนื่อง 2 สัปดาห์+ | 60% | 40% |
| Core เริ่มมีสัญญาณ Saturation | 50% | 50% (เร่งหา Winner ใหม่มาทดแทน) |

### Roadmap ตัวอย่าง 8 สัปดาห์

| สัปดาห์ | กิจกรรม Core | กิจกรรม Satellite |
|---|---|---|
| 1-2 | Vertical Scale ตาม 20% Rule ทุก 3 วัน | สร้าง Ad Set ใหม่ 2 กลุ่ม ทดสอบ Audience ใหม่ |
| 3-4 | ต่อเนื่อง Vertical Scale, เช็ก Frequency ทุกวัน | เพิ่ม Creative ใหม่ 3-5 ตัวใน Satellite ที่มีสัญญาณดี |
| 5-6 | ถ้า Core เริ่ม Saturate ให้ลดอัตราการเพิ่มงบลง | โปรโมท Satellite ที่ชนะให้กลายเป็น Core ตัวใหม่ (เริ่ม Vertical Scale ให้ตัวนั้น) |
| 7-8 | รักษาระดับงบ Core หลายตัวให้สมดุล | เริ่มหา Satellite รุ่นต่อไปเพื่อวนกลับไปขั้นที่ 1 |

### ทำไม Roadmap แบบนี้ยั่งยืนกว่าการ Scale แบบเดียว

การมี Satellite วิ่งคู่กับ Core ตลอดเวลาทำให้เมื่อ Core ตัวใดตัวหนึ่ง Saturate หรือ Fatigue ในที่สุด (ซึ่งเกิดขึ้นแน่นอนตามกฎ Diminishing Returns ใน Step 575) จะมี Winner ตัวใหม่พร้อมเข้ามาแทนที่ทันที ไม่ต้องเริ่มหาใหม่จากศูนย์ทำให้รายได้รวมไม่ตกฮวบ

### ข้อผิดพลาดที่พบบ่อย

- ทุ่มงบ 100% ไปที่ Core โดยไม่มี Satellite เลย พอ Core Saturate รายได้รวมตกฮวบและต้องเริ่มหา Winner ใหม่แบบฉุกละหุก
- สร้าง Satellite มากเกินไปจนงบกระจายเบาเกินกว่าจะจบ Learning Phase ในแต่ละกลุ่ม

### เกณฑ์การเลื่อนสถานะ Satellite เป็น Core ตัวใหม่

ไม่ใช่ทุก Satellite ที่มีตัวเลขดีจะควรเลื่อนเป็น Core ทันที ควรใช้เกณฑ์ที่ชัดเจนเพื่อไม่ให้ตัดสินใจจากความผันผวนระยะสั้น:

| เกณฑ์ | ค่าที่ควรผ่านก่อนเลื่อนเป็น Core |
|---|---|
| ระยะเวลารันต่อเนื่อง | อย่างน้อย 10-14 วัน (ผ่าน Learning Phase เต็มรูปแบบแล้ว) |
| Cost per Result เทียบกับ Core ตัวหลัก | ใกล้เคียงหรือดีกว่า Core ตัวหลักไม่เกิน ±20% |
| Frequency | ต่ำกว่า Benchmark สัญญาณ Saturation (ทบทวน Step 575) |
| Sample Size (จำนวน Result สะสม) | อย่างน้อย 50-100 Events เพื่อความน่าเชื่อถือทางสถิติ |
| Audience Overlap กับ Core ตัวอื่น | ต่ำกว่า 20% (เช็กผ่าน Audience Overlap Tool ใน Business Manager) |

ถ้า Satellite ผ่านเกณฑ์ทั้งหมดนี้ ให้เริ่มกระบวนการ Vertical Scaling กับมันเหมือนที่ทำกับ Core ตัวอื่น (ย้อนกลับไปทำตาม Step 571) และปรับสัดส่วนงบ Core/Satellite ใหม่ตามที่ระบุใน Step 574

## Step 575: Diminishing Returns และสัญญาณ Audience Saturation

### กฎของ Diminishing Returns คืออะไร

ทุก Audience มี "เพดาน" ตามธรรมชาติ — ยิ่งเพิ่มงบเข้าไปในกลุ่มเดิมมากเท่าไหร่ ผลตอบแทนต่อบาทที่ลงทุนเพิ่มจะยิ่งลดลงเรื่อยๆ (ไม่ใช่เพิ่มขึ้นเป็นเส้นตรงตลอดไป) เพราะกลุ่มคนที่มีโอกาสซื้อสูงสุดในกลุ่มนั้นถูก "เก็บ" ไปหมดแล้วในช่วงต้น ที่เหลือคือคนที่มีโอกาสซื้อต่ำลงเรื่อยๆ

### ตัวอย่างตัวเลขจริงแสดง Diminishing Returns

Lookalike 1% Audience ขนาด 900,000 คน:

| งบ/วัน | Purchases/วัน | Cost per Purchase | Purchase เพิ่มขึ้นต่อ 500 บาทที่เพิ่ม |
|---|---|---|---|
| 1,000 บาท | 8 | 125 บาท | — |
| 1,500 บาท | 11 | 136 บาท | +3 |
| 2,000 บาท | 13 | 154 บาท | +2 |
| 2,500 บาท | 14 | 179 บาท | +1 |
| 3,000 บาท | 14.5 | 207 บาท | +0.5 |

เห็นชัดว่าทุก 500 บาทที่เพิ่มขึ้น จำนวน Purchase ที่ได้เพิ่มลดลงเรื่อยๆ (จาก +3 เหลือ +0.5) นี่คือ Diminishing Returns ที่เกิดขึ้นจริงตามธรรมชาติของ Auction — ไม่ใช่ปัญหาที่แก้ไขได้ด้วยการปรับ Creative หรือ Bid แต่เป็นข้อจำกัดของ Audience Size

### สัญญาณ Audience Saturation ที่ต้องจับตา

| สัญญาณ | รายละเอียด |
|---|---|
| Frequency พุ่งสูงต่อเนื่องแม้ Audience Size ใหญ่ | คนในกลุ่มเห็นซ้ำมากขึ้นเพราะ Reach ใหม่หาไม่ได้แล้ว |
| CPM สูงขึ้นเรื่อยๆ แม้ไม่มีปัจจัยไฮซีซัน/คู่แข่งเพิ่ม | Auction ในกลุ่มนี้แข่งขันกับตัวเองมากขึ้น (คุณแข่งกับ Ad ตัวอื่นของคุณเองด้วย) |
| Cost per Result ไต่ขึ้นทุกครั้งที่เพิ่มงบ แม้เพิ่มตาม 20% Rule แล้ว | เพดานธรรมชาติของ Audience ถูกแตะแล้ว ไม่ใช่ปัญหาการ Scale ผิดวิธี |
| Reach เติบโตช้าลงมากเทียบกับ Impressions ที่ยังโตต่อเนื่อง | กำลังฉายซ้ำคนกลุ่มเดิมมากขึ้นเรื่อยๆ ไม่ได้ขยายไปคนใหม่แล้ว |

### สิ่งที่ควรทำเมื่อเจอสัญญาณ Saturation

1. หยุด Vertical Scaling ในกลุ่มนั้นทันที (อย่าฝืนเพิ่มงบต่อ)
2. เปลี่ยนไปใช้ Horizontal Scaling หา Audience ใหม่ (ทบทวน Step 572)
3. พิจารณาลดงบกลุ่มที่ Saturate ลงเล็กน้อยเพื่อคง Efficiency แล้วย้ายงบส่วนต่างไปยัง Satellite ที่มีศักยภาพ

### ข้อจำกัดพิเศษของการ Scale Retargeting Pool

Retargeting Pool มีธรรมชาติที่ต่างจาก Cold Audience อย่างมากเมื่อพูดถึง Saturation — เพราะ Pool ขนาดถูกกำหนดโดย "จำนวนคนที่ทำพฤติกรรมนั้นจริง" (เช่น คนที่ Add to Cart ใน 30 วันที่ผ่านมา) ไม่สามารถขยายได้ตามใจแบบ Cold Audience ที่แค่เพิ่ม Interest ก็ขยายได้ทันที

**ตัวอย่างข้อจำกัดของ Retargeting Pool:**

| ประเภท Pool | ขนาด Pool โดยประมาณ | งบสูงสุดที่ Pool นี้รองรับได้แบบมีเสถียรภาพ |
|---|---|---|
| Video Viewer 25%+ (30 วัน) | 150,000 คน | 800-1,200 บาท/วัน |
| Website Visitor (30 วัน) | 60,000 คน | 400-600 บาท/วัน |
| Add to Cart (14 วัน) | 8,000 คน | 100-200 บาท/วัน |
| Checkout Initiated (7 วัน) | 1,500 คน | 30-60 บาท/วัน |

เห็นได้ชัดว่า Pool ที่แคบลง (Checkout Initiated) รองรับงบได้น้อยมาก การพยายาม Vertical Scale งบเข้า Pool เล็กเกินไปจะ Saturate เกือบจะในทันที — วิธีแก้คือขยาย Window ของ Retargeting (เช่น จาก 7 วัน เป็น 14-30 วัน) เพื่อเพิ่มขนาด Pool ก่อน Scale งบเพิ่ม หรือยอมรับว่า Pool นี้มีเพดานงบตามธรรมชาติและไม่ควรฝืนเพิ่มเกินกว่านั้น

### ข้อผิดพลาดที่พบบ่อย

- ฝืนเพิ่มงบต่อในกลุ่มที่ Saturate แล้วเพราะ "เมื่อก่อนมันเคยดี" ทำให้ Cost per Result แพงขึ้นเรื่อยๆโดยไม่จำเป็น
- ไม่แยกระหว่าง Saturation (ปัญหาเชิงโครงสร้างของ Audience) กับ Ad Fatigue (ปัญหาที่ครีเอทีฟล้า แก้ได้ด้วยการรีเฟรช Creative) ทำให้แก้ปัญหาผิดทาง
- พยายาม Vertical Scale Retargeting Pool ที่มีขนาดเล็กมาก (เช่น Checkout Initiated 7 วัน) โดยไม่ขยาย Window ก่อน ทำให้ Saturate เกือบจะในทันทีที่เพิ่มงบ

### เส้นกราฟ Diminishing Returns แบบเต็มรูปแบบ (Audience ขนาดต่างกัน)

ความเร็วที่ Diminishing Returns เกิดขึ้นไม่เท่ากันในทุก Audience — Audience ที่เล็กจะ Saturate เร็วกว่า Audience ที่ใหญ่มาก ตารางด้านล่างเปรียบเทียบ Audience 3 ขนาดที่ Scale งบในอัตราเดียวกัน:

| งบ/วัน | Audience เล็ก (200,000 คน) Cost/Purchase | Audience กลาง (900,000 คน) Cost/Purchase | Audience ใหญ่ (3.5 ล้านคน) Cost/Purchase |
|---|---|---|---|
| 1,000 บาท | 140 บาท | 125 บาท | 118 บาท |
| 2,000 บาท | 210 บาท (+50%) | 154 บาท (+23%) | 130 บาท (+10%) |
| 4,000 บาท | 385 บาท (+83%) | 207 บาท (+34%) | 148 บาท (+14%) |
| 8,000 บาท | ไม่วิ่ง/Cost พุ่งเกินควบคุม | 310 บาท (+50%) | 175 บาท (+18%) |

เห็นชัดว่า Audience เล็ก (200,000 คน) เข้าสู่ Diminishing Returns เร็วมากและรุนแรงกว่า ในขณะที่ Audience ใหญ่ (3.5 ล้านคน) ยังรับงบที่เพิ่มขึ้นได้อย่างมีเสถียรภาพกว่ามาก — บทเรียนคือ **ขนาด Audience ตั้งแต่แรกมีผลกับ "เพดาน" ของ Vertical Scaling โดยตรง** ถ้าต้องการ Scale งบสูงมาก ควรเลือก Audience ที่มีขนาดใหญ่พอตั้งแต่ต้น หรือใช้ Horizontal Scaling ควบคู่กันเร็วกว่าปกติสำหรับ Audience เล็ก

### ข้อผิดพลาดที่พบบ่อยเพิ่มเติม

- เลือก Audience เล็กเกินไปตั้งแต่ต้นแล้วพยายาม Vertical Scale หนักๆ ทั้งที่ควรใช้ Horizontal Scaling เป็นหลักสำหรับ Audience ขนาดนี้ตั้งแต่แรก
- ไม่เคยเทียบอัตราการเพิ่มขึ้นของ Cost per Purchase ต่อการเพิ่มงบ (% เทียบ %) ทำให้มองไม่เห็นว่ากำลังเข้าสู่ช่วง Diminishing Returns เร็วกว่าที่คิด

## Step 576: การ Scale ข้ามพื้นที่ทางภูมิศาสตร์ (Geographic/International Scaling)

### เมื่อไหร่ควรพิจารณา Geographic Scaling

เมื่อ Audience ในพื้นที่เดิม (เช่น กรุงเทพฯ+ปริมณฑล) เริ่มเข้าใกล้ Saturation และธุรกิจมีความสามารถรองรับลูกค้าจากพื้นที่ใหม่ได้ (สต็อกสินค้า ระบบขนส่ง ทีมแอดมิน) — Geographic Scaling คือรูปแบบหนึ่งของ Horizontal Scaling ที่ขยายไปยัง "พื้นที่ใหม่" แทน "กลุ่มความสนใจใหม่"

### ข้อพิจารณาสำคัญก่อน Scale ข้ามพื้นที่

**1. ความแตกต่างของ CPM ตามภูมิภาค** — กรุงเทพฯมักมี CPM สูงกว่าจังหวัดอื่นเพราะมีคู่แข่งแย่งชิงมากกว่า การขยายไปหัวเมืองรองอาจได้ CPM ถูกกว่าอย่างมีนัยสำคัญ

**2. Logistics และเวลาส่งสินค้า** — พื้นที่ไกลอาจมีค่าส่งสูงขึ้นหรือใช้เวลานานขึ้น กระทบ Conversion Rate และความพึงพอใจลูกค้า

**3. ความแตกต่างทางวัฒนธรรม/ภาษาถิ่น** — ครีเอทีฟที่ใช้ได้ผลดีในกรุงเทพฯอาจต้องปรับ Copy ให้เข้ากับบริบทท้องถิ่นมากขึ้น

**4. การขยายไปต่างประเทศ** — ต้องพิจารณาภาษา สกุลเงิน วิธีชำระเงินที่นิยมในประเทศนั้น (เช่น ประเทศเพื่อนบ้านอาจไม่ใช้ PromptPay) กฎหมายโฆษณาท้องถิ่น และพฤติกรรมผู้บริโภคที่ต่างกันโดยสิ้นเชิง — ควรถือเป็นการทดสอบตลาดใหม่ทั้งหมด ไม่ใช่แค่การ Duplicate แคมเปญเดิมแล้วเปลี่ยน Location

### ตัวอย่างตัวเลขเปรียบเทียบการ Scale ข้ามพื้นที่

| พื้นที่ | CPM (บาท) | Conversion Rate | ค่าส่งเฉลี่ย (บาท) | Cost per Purchase |
|---|---|---|---|---|
| กรุงเทพฯ+ปริมณฑล | 62 | 3.8% | 35 | 145 บาท |
| หัวเมืองรอง (เชียงใหม่, ขอนแก่น, ภูเก็ต) | 41 | 3.1% | 55 | 138 บาท |
| พื้นที่ห่างไกล (จังหวัดเล็ก) | 33 | 2.0% | 85 | 175 บาท |

น่าสนใจว่าหัวเมืองรองให้ Cost per Purchase ถูกกว่ากรุงเทพฯเล็กน้อย แม้ Conversion Rate ต่ำกว่า เพราะ CPM ที่ถูกกว่าชดเชยได้เกินพอ — แต่พื้นที่ห่างไกลกลับแพงกว่าเพราะค่าส่งสูงและ Conversion Rate ต่ำเกินไปจะชดเชย CPM ที่ถูก

### ข้อผิดพลาดที่พบบ่อย

- Duplicate แคมเปญไปทุกจังหวัดพร้อมกันโดยไม่ทดสอบเป็นกลุ่มย่อยก่อน ทำให้เจอปัญหา Logistics ที่ไม่คาดคิดในหลายพื้นที่พร้อมกัน
- ขยายไปต่างประเทศโดยใช้ครีเอทีฟและ Copy เดิมทั้งหมดแบบแปลตรงตัว ไม่ปรับให้เข้ากับบริบทวัฒนธรรมท้องถิ่น

## Step 577: ไทม์ไลน์การ Scale แบบวันต่อวัน (ตัวอย่างจริง)

### สถานการณ์ตั้งต้น

Ad Set "Lookalike 1% — Purchase" งบ 1,000 บาท/วัน Cost per Purchase 130 บาท (Break-even 250 บาท) ต้องการ Scale ไปที่ 5,000 บาท/วัน ภายใน 30 วัน ด้วยการผสม Vertical + Horizontal

### ตารางไทม์ไลน์ 30 วัน

| วันที่ | กิจกรรม | งบ Core (บาท) | งบ Satellite (บาท) | หมายเหตุ |
|---|---|---|---|---|
| 1-3 | เพิ่มงบ Core 20% (1,000→1,200), เริ่ม Satellite 2 กลุ่ม | 1,200 | 400 (200x2) | เช็ก Frequency ทุกวัน |
| 4-6 | เพิ่มงบ Core 20% (1,200→1,440) ถ้าเสถียร | 1,440 | 500 | Satellite เริ่มมีข้อมูลพอวิเคราะห์ |
| 7-9 | เพิ่มงบ Core 20% (1,440→1,728) | 1,728 | 600 | เช็ก Satellite ตัวไหนมีสัญญาณดี เพิ่มงบให้ |
| 10-12 | เพิ่มงบ Core 20% (1,728→2,074) | 2,074 | 800 | ปิด Satellite ที่ไม่มีสัญญาณเลย |
| 13-15 | เพิ่มงบ Core 20% (2,074→2,489) | 2,489 | 1,000 | Satellite ที่ดีเริ่มโปรโมทเป็น Core ตัวที่ 2 |
| 16-18 | เพิ่มงบ Core 20% (2,489→2,987) | 2,987 | 1,200 | เช็ก Diminishing Returns เริ่มปรากฏหรือยัง |
| 19-21 | ถ้ายังเสถียร เพิ่มงบ Core 20% (2,987→3,584) | 3,584 | 1,400 | เริ่มมี Core 2 ตัว (Lookalike + Satellite ที่ชนะ) |
| 22-24 | กระจายงบระหว่าง Core 2 ตัว ตาม Performance | Core 1: 2,500 / Core 2: 1,500 | 1,400 | บริหารความเสี่ยงด้วยการมี Core มากกว่า 1 ตัว |
| 25-27 | เพิ่มงบ Core ทั้งสองตัวตาม 20% Rule | Core 1: 3,000 / Core 2: 1,800 | 1,500 | รวมงบ ~6,300 (เกินเป้าเล็กน้อย ปรับลงเล็กน้อยได้) |
| 28-30 | ปรับสมดุลให้รวมงบใกล้เคียง 5,000 | Core 1: 2,800 / Core 2: 1,700 | 1,000 | ทบทวนแผน 30 วันถัดไป |

### บทเรียนจากไทม์ไลน์นี้

1. การ Scale จาก 1,000 เป็น 5,000 บาท/วัน (5 เท่า) ใช้เวลาประมาณ 30 วัน ไม่ใช่วันเดียว — นี่คือความเร็วที่ปลอดภัยตามธรรมชาติของ 20% Rule
2. ตลอดเส้นทางมี Satellite วิ่งคู่กันเสมอ ทำให้เมื่อถึงวันที่ 22 มี Core ตัวที่ 2 พร้อมมาแบ่งความเสี่ยงแล้ว
3. งบสุดท้ายไม่จำเป็นต้องตรงเป้า 5,000 บาทเป๊ะๆ — ความยืดหยุ่นและการปรับตามสัญญาณจริงสำคัญกว่าการยึดติดตัวเลขเป้าหมาย

### ข้อผิดพลาดที่พบบ่อย

- ยึดติดกับไทม์ไลน์ตายตัวโดยไม่ปรับตามสัญญาณจริงที่เกิดขึ้น (เช่น เจอ Saturation ก่อนกำหนดแต่ยังฝืนเพิ่มงบตามตาราง)
- ไม่เผื่อเวลาสำหรับ Satellite ให้ผ่าน Learning Phase ก่อนตัดสินใจว่าจะโปรโมทเป็น Core หรือไม่

## Step 578: การจัดการความเสี่ยงระหว่าง Scale

### กฎเหล็ก: ห้าม Scale 100% เข้า Ad Set เดียว

ไม่ว่า Ad Set นั้นจะดูดีแค่ไหน การทุ่มงบทั้งหมดไปที่จุดเดียวมีความเสี่ยงสูงมาก เพราะ:

1. **ความเสี่ยงจาก Saturation ที่มาถึงไม่รู้ตัว** — วันที่ Ad Set เดียวที่ Saturate จะทำให้รายได้ทั้งธุรกิจตกฮวบทันที ไม่มี Backup
2. **ความเสี่ยงจากการถูก Disable/Restrict** — ถ้า Ad Account หรือ Ad Set นั้นมีปัญหานโยบายกะทันหัน (ทบทวน Part 020) ธุรกิจจะไม่มีรายได้จากโฆษณาเลยในทันที
3. **ความเสี่ยงจากการเปลี่ยนแปลง Algorithm** — Meta ปรับ Algorithm บ่อย การพึ่งพา Ad Set เดียวทำให้ธุรกิจเปราะบางต่อการเปลี่ยนแปลงนั้นมากเกินไป

### กรอบการกระจายความเสี่ยงที่แนะนำ

| ระดับความเสี่ยงที่ยอมรับได้ | สัดส่วนงบสูงสุดต่อ Ad Set เดียว | จำนวน Core ขั้นต่ำที่ควรมี |
|---|---|---|
| อนุรักษ์นิยม (ธุรกิจพึ่งพาโฆษณา 100%) | ไม่เกิน 25% ของงบรวม | 4+ Core |
| กลาง | ไม่เกิน 35-40% ของงบรวม | 3 Core |
| ยอมรับความเสี่ยงได้มากกว่า (มีรายได้จากช่องทางอื่นด้วย) | ไม่เกิน 50% ของงบรวม | 2 Core |

### ตัวอย่างการกระจายความเสี่ยงจริง

ธุรกิจงบรวม 10,000 บาท/วัน ไม่ควรมี Ad Set เดียวรับงบเกิน 3,500-4,000 บาท (35-40%) แม้ Ad Set นั้นจะเป็น Winner ที่ดีที่สุดก็ตาม ควรกระจายเป็น:

| Ad Set | งบ/วัน | บทบาท |
|---|---|---|
| Core 1 (Lookalike 1% เดิม) | 3,500 บาท | Winner หลัก |
| Core 2 (Interest ที่โปรโมทจาก Satellite) | 2,500 บาท | Winner รอง |
| Core 3 (Retargeting) | 1,500 บาท | เสถียร คงที่ |
| Satellite (ทดสอบ Audience ใหม่) | 2,500 บาท | หา Winner ตัวต่อไป |

### ความเสี่ยงเชิง Correlation ที่มักถูกมองข้าม

การกระจายงบเป็นหลาย Ad Set ยังไม่พอถ้าทุก Ad Set นั้น "เสี่ยงพร้อมกัน" จากปัจจัยเดียวกัน เช่น ถ้า Core ทั้ง 4 ตัวใช้ Pixel เดียวกันบนเว็บไซต์เดียวกัน การที่เว็บไซต์ล่มหรือ Pixel มีปัญหาจะกระทบทุก Core พร้อมกันในทันที แม้จะกระจายงบข้าม Ad Set ดีแล้วก็ตาม หลักการกระจายความเสี่ยงที่สมบูรณ์ควรพิจารณาความเสี่ยงเชิง Correlation ด้วย ไม่ใช่แค่จำนวน Ad Set:

| ปัจจัยเสี่ยงร่วม | ผลกระทบถ้าเกิดปัญหา | วิธีลดความเสี่ยง |
|---|---|---|
| Pixel/Landing Page เดียวกันทุก Ad Set | ทุก Core ล้มพร้อมกันถ้าเว็บ/Pixel มีปัญหา | มี Backup Landing Page หรือ Server-Side Tracking สำรอง (ทบทวน Part 090) |
| Ad Account เดียวกันทั้งหมด | ถ้าบัญชีถูก Disable ทุก Core หยุดพร้อมกัน | เตรียม Backup Ad Account ที่ Warm-up ไว้ล่วงหน้า |
| ครีเอทีฟชุดเดียวกันใช้ในหลาย Core | Ad Fatigue เกิดพร้อมกันทุก Core | ใช้ครีเอทีฟที่แตกต่างกันบางส่วนในแต่ละ Core |
| Payment Method เดียวกัน | ถ้าบัตร/วิธีชำระเงินมีปัญหา ทุกแคมเปญหยุดพร้อมกัน | มีวิธีชำระเงินสำรองที่ผูกไว้ล่วงหน้า |

### ข้อผิดพลาดที่พบบ่อย

- ทุ่มงบ 80-90% ไปที่ Ad Set เดียวเพราะ "มันดีที่สุดตอนนี้" โดยไม่มีแผนสำรอง
- ไม่มี Backup Ad Account/Page/Pixel เผื่อกรณีบัญชีหลักถูกจำกัด (ทบทวน Part 020 เรื่อง Backup Strategy) ในช่วงที่กำลัง Scale งบสูง ความเสี่ยงจากการถูก Disable ยิ่งกระทบหนักกว่าช่วงงบน้อย

### การวางแผน Creative Refresh Cadence ควบคู่กับการ Scale

ความเสี่ยงอีกจุดที่มักถูกมองข้ามระหว่าง Scale คือ **ครีเอทีฟล้าเร็วขึ้นตามงบที่เพิ่มขึ้น** เพราะงบที่มากขึ้นหมายถึง Impressions ต่อวันที่มากขึ้น ทำให้ Frequency ไต่สูงเร็วกว่าช่วงงบน้อยมาก ตารางด้านล่างแสดงความสัมพันธ์ระหว่างระดับงบกับความถี่ที่ควรเติมครีเอทีฟใหม่:

| งบ/วันของ Ad Set | Impressions/วันโดยประมาณ (CPM 50 บาท) | ความถี่ที่ควรเติม Creative ใหม่ |
|---|---|---|
| 1,000 บาท | 20,000 | ทุก 10-14 วัน |
| 3,000 บาท | 60,000 | ทุก 7-10 วัน |
| 8,000 บาท | 160,000 | ทุก 5-7 วัน |
| 15,000+ บาท | 300,000+ | ทุก 3-5 วัน |

หลักการคือยิ่งงบสูง ยิ่งต้องมี "คลัง Creative" สำรองมากขึ้นและเติมบ่อยขึ้น ธุรกิจที่ Scale โดยไม่เตรียม Creative Pipeline ให้พร้อม (ทบทวน Part 043-044 เรื่อง Creative Testing Framework) มักเจอ Ad Fatigue เร็วกว่าที่คาดและ Cost per Result พุ่งขึ้นทั้งที่โครงสร้างงบ/Audience ถูกต้องแล้ว

### ข้อผิดพลาดที่พบบ่อยเพิ่มเติม

- Scale งบเพิ่มขึ้นเรื่อยๆโดยไม่เพิ่มจำนวนครีเอทีฟใหม่ในสัดส่วนที่สัมพันธ์กัน ทำให้ Ad Fatigue มาเร็วกว่าที่วางแผนไว้มาก
- ไม่มีทีม/ระบบผลิตครีเอทีฟที่รองรับความเร็วในการ Scale งบ ทำให้ต้องหยุด Scale เพราะ "ไม่มีครีเอทีฟใหม่จะใส่" ทั้งที่งบและ Audience ยังรองรับได้อีก

## Step 579: ข้อผิดพลาดที่พบบ่อยที่สุดในการ Scale

รวบรวมข้อผิดพลาดที่พบบ่อยที่สุดจากทุก Step ในบทนี้ พร้อมสรุปสั้นเพื่อเป็น Checklist เตือนใจ:

1. **Scale เร็วเกินไป (เพิ่มงบเกิน 20% ในครั้งเดียว)** — ทำให้ Learning Phase รีเซ็ตและ Cost per Result พุ่งขึ้นชั่วคราวโดยไม่จำเป็น
2. **Scale ทั้งหมดเข้า Ad Set เดียว** — ไม่มีการกระจายความเสี่ยง เมื่อเกิดปัญหาใดๆรายได้ทั้งธุรกิจล้มพร้อมกัน
3. **ไม่แยก Saturation กับ Ad Fatigue** — แก้ปัญหาผิดวิธี (เช่น เปลี่ยนครีเอทีฟเมื่อปัญหาจริงคือ Audience หมด หรือขยาย Audience เมื่อปัญหาจริงคือครีเอทีฟล้า)
4. **ไม่มี Satellite วิ่งคู่กับ Core เลย** — พอ Core ถึงจุด Saturate ไม่มี Winner ตัวใหม่มาทดแทนทันที
5. **ตัดสินใจจากตัวเลข 1-2 วันหลังปรับงบ** — ความผันผวนชั่วคราวจาก Learning ทำให้ตกใจและถอยกลับเร็วเกินไปทั้งที่ควรรอ 3+ วัน
6. **Geographic Scaling แบบไม่ทดสอบก่อน** — ขยายไปทุกพื้นที่ทีเดียวโดยไม่รู้ Logistics/Conversion Rate ของพื้นที่ใหม่มาก่อน
7. **ไม่มีแผนสำรอง Ad Account/Page ระหว่าง Scale งบสูง** — ความเสี่ยงจากการถูกจำกัดบัญชีกระทบรุนแรงกว่าช่วงงบน้อย
8. **ไม่เตรียม Creative Pipeline ให้สัมพันธ์กับความเร็วในการ Scale** — งบโตเร็วกว่าจำนวนครีเอทีฟใหม่ที่ผลิตได้ ทำให้ Ad Fatigue มาเร็วกว่าที่ควร

### ตารางสรุปเปรียบเทียบ ROI ระหว่าง Vertical และ Horizontal Scaling (ภาพรวม 30 วัน)

เพื่อให้เห็นภาพชัดว่าทั้งสองกลยุทธ์ให้ผลตอบแทนต่างกันอย่างไรในกรอบเวลาเดียวกัน สมมติธุรกิจมีงบเริ่มต้น 1,000 บาท/วัน และทดลองแยกกลยุทธ์บนเงินก้อนเดียวกัน (จำลองสถานการณ์เพื่อการเรียนรู้):

| ตัวชี้วัด (สะสม 30 วัน) | Vertical Scaling อย่างเดียว | Horizontal Scaling อย่างเดียว | Hybrid (Core-Satellite) |
|---|---|---|---|
| งบรวมที่ใช้ | 75,000 บาท | 75,000 บาท | 75,000 บาท |
| จำนวน Purchase รวม | 480 | 410 | 545 |
| Cost per Purchase เฉลี่ย | 156 บาท | 183 บาท | 138 บาท |
| ความเสี่ยงจาก Ad Set เดียวล้ม | สูง (พึ่งพา Ad Set เดียวเกือบทั้งหมด) | ต่ำ (กระจายในหลาย Ad Set) | ต่ำ-กลาง |
| จำนวน Winner ใหม่ที่ค้นพบ | 0 | 3 | 2 |

Hybrid Model ให้ผลลัพธ์ดีที่สุดในทุกมิติ เพราะได้ประโยชน์จากความเร็วของ Vertical (ใช้ประโยชน์จาก Winner ที่พิสูจน์แล้วทันที) ผสมกับความปลอดภัยและการค้นพบสิ่งใหม่ของ Horizontal — นี่คือเหตุผลที่ Part นี้แนะนำ Core-Satellite Model เป็นแนวทางหลักตั้งแต่ Step 574

## Case Study: ร้านขายอุปกรณ์ออกกำลังกายที่ Scale พังแล้วกลับมาแก้ไขได้

ร้านขายอุปกรณ์ออกกำลังกายออนไลน์เจอ Ad Set ที่ชนะ (Lookalike 1.5%) ทำ Cost per Purchase ได้ 95 บาท (Break-even 180 บาท) จากงบ 600 บาท/วัน เจ้าของร้านตื่นเต้นมากและเพิ่มงบทันทีเป็น 3,000 บาท/วัน (เพิ่ม 400% ในครั้งเดียว) หวังจะได้กำไรเพิ่มขึ้น 5 เท่าทันที

**ผลที่เกิดขึ้นจริง:** วันแรกหลังเพิ่มงบ Ad Set เข้าสู่สถานะ Learning ใหม่ทั้งหมด Cost per Purchase พุ่งขึ้นเป็น 340 บาท (แพงกว่า Break-even) ต่อเนื่อง 4 วัน เจ้าของร้านตกใจและลดงบกลับไปที่ 600 บาทเหมือนเดิม แต่ผลลัพธ์กลับไม่ดีเท่าเดิมด้วย เพราะ Ad Set ต้องผ่าน Learning Phase ใหม่อีกรอบจากการเปลี่ยนงบกลับไปกลับมา

**การแก้ไขเมื่อเรียนรู้หลักการ Scale ที่ถูกต้อง:** เริ่มใหม่จากงบ 600 บาท ปล่อยให้กลับสู่ Active อีกครั้ง (ใช้เวลา 5 วัน) จากนั้นเพิ่มงบตาม 20% Rule ทุก 3 วัน (600→720→864→1,037→1,244→...) พร้อมสร้าง Satellite 2 กลุ่มคู่กันไปด้วย ภายใน 25 วัน งบขึ้นไปถึง 2,800 บาท/วัน อย่างเสถียร Cost per Purchase อยู่ที่ 115 บาท (แพงขึ้นจาก 95 บาทเล็กน้อยตามธรรมชาติของ Diminishing Returns แต่ยัง Break-even ได้สบาย)

**บทเรียน:** ความตื่นเต้นเมื่อเจอ Winner เป็นสิ่งที่เข้าใจได้ แต่การ Scale ต้องใช้ระบบ ไม่ใช่อารมณ์ — ความเร็วที่ "ดูช้า" ของ 20% Rule แท้จริงคือความเร็วที่ปลอดภัยที่สุดในระยะยาว

### ระยะที่ 2 ของ Case Study: เมื่อ Core เริ่ม Saturate หลังวันที่ 45

หลังจากงบขึ้นไปถึง 2,800 บาท/วันอย่างเสถียรตามที่เล่าไปแล้ว ร้านค้าเดินหน้าต่อด้วยการ Vertical Scale ตาม 20% Rule ต่อเนื่องจนถึงวันที่ 45 งบขึ้นไปถึง 5,600 บาท/วัน แต่เริ่มสังเกตสัญญาณ Saturation ตามที่เรียนใน Step 575:

| ตัวชี้วัด | วันที่ 30 (งบ 2,800 บาท) | วันที่ 45 (งบ 5,600 บาท) |
|---|---|---|
| Frequency | 2.3 | 5.1 |
| CPM | 52 บาท | 71 บาท |
| Cost per Purchase | 115 บาท | 198 บาท |

ทีมงานจับสัญญาณได้ทันเวลาเพราะเช็ก Frequency เป็นกิจวัตร (ทบทวน Part 056) จึงหยุด Vertical Scale ทันทีที่งบ 5,600 บาท และหันไปโฟกัส Satellite ที่เตรียมไว้คู่กันตั้งแต่ต้น พบว่า Satellite กลุ่ม "Lookalike 3-7%" มีตัวเลขผ่านเกณฑ์การเลื่อนเป็น Core ตามตารางใน Step 574 พอดี จึงเลื่อนเป็น Core ตัวที่ 2 และเริ่ม Vertical Scale ให้ตัวใหม่นี้ต่อ ในขณะที่ลดงบ Core ตัวเดิมลงเล็กน้อย (จาก 5,600 เหลือ 4,500 บาท) เพื่อคุม Frequency ให้กลับสู่ระดับปกติ

**ผลลัพธ์รวมหลังปรับ 2 สัปดาห์:** งบรวมทั้งสอง Core อยู่ที่ 7,200 บาท/วัน (สูงกว่าจุดที่เคย Saturate เดิม) แต่ Cost per Purchase เฉลี่ยกลับมาอยู่ที่ 128 บาท เพราะกระจายงบข้าม Core 2 ตัวที่ไม่ Overlap กันมาก — นี่คือตัวอย่างที่แสดงว่า Core-Satellite Model ไม่ใช่แค่ทฤษฎี แต่ใช้แก้ปัญหา Saturation ได้จริงเมื่อนำมาปฏิบัติอย่างมีวินัย

## Checklist ท้ายบท

- [ ] เข้าใจกลไก Vertical Scaling และ 20% Rule อย่างถ่องแท้
- [ ] เข้าใจกลไก Horizontal Scaling ทั้ง 3 รูปแบบ (Audience, Creative, Placement Expansion)
- [ ] รู้กรอบการตัดสินใจว่าเมื่อไหร่ควรใช้ Vertical เมื่อไหร่ควรใช้ Horizontal
- [ ] เข้าใจแนวคิด Core-Satellite Scaling Model
- [ ] แยกสัญญาณ Audience Saturation จาก Ad Fatigue ได้
- [ ] มีกรอบการจัดการความเสี่ยง ไม่ Scale 100% เข้า Ad Set เดียว
- [ ] สามารถเขียน Scaling Timeline แบบวันต่อวันของตัวเองได้
- [ ] จดจำข้อผิดพลาดที่พบบ่อยที่สุด 8 ข้อใน Step 579 ได้ทั้งหมด
- [ ] รู้เกณฑ์การเลื่อน Satellite เป็น Core ตัวใหม่ทั้ง 5 ข้อ
- [ ] เข้าใจข้อจำกัดพิเศษของการ Scale Retargeting Pool ที่ต่างจาก Cold Audience
- [ ] วางแผน Creative Refresh Cadence ให้สัมพันธ์กับระดับงบที่ Scale ไป
- [ ] เช็ก Audience Overlap ก่อนทำ Horizontal Scaling ทุกครั้ง
- [ ] ประเมินความเสี่ยงเชิง Correlation (Pixel, Ad Account, Payment Method) ไม่ใช่แค่จำนวน Ad Set ที่กระจายงบ

## Workshop / แบบฝึกหัด

**แบบฝึกหัดที่ 1:** ทำ Workshop เต็มรูปแบบตาม Step 580 โดยใช้ข้อมูลตั้งต้นที่ให้ไว้ หรือใช้ข้อมูลจากแคมเปญจริงของคุณเอง

**แบบฝึกหัดที่ 2:** เลือก Ad Set ที่ชนะในบัญชีจริงของคุณ (หรือสมมติสถานการณ์) แล้วคำนวณขั้นบันได 20% Rule จากงบปัจจุบันไปสู่เป้าหมายที่ต้องการ

**แบบฝึกหัดที่ 3:** ออกแบบ Satellite Plan จำนวน 3 กลุ่มสำหรับ Ad Set Core ของคุณ ระบุว่าจะทดสอบ Audience/Creative/Placement อะไรในแต่ละกลุ่ม

**แบบฝึกหัดที่ 4:** เขียนกฎการกระจายความเสี่ยงของตัวเอง (สัดส่วนงบสูงสุดต่อ Ad Set เดียว) ตามระดับความเสี่ยงที่ธุรกิจของคุณยอมรับได้

**แบบฝึกหัดที่ 5:** ถ้าธุรกิจของคุณมี Retargeting Pool ที่ใช้อยู่ ให้ประมาณขนาด Pool ของแต่ละ Window (7/14/30 วัน) แล้วคำนวณงบสูงสุดที่ Pool นั้นน่าจะรองรับได้แบบมีเสถียรภาพตามหลักการใน Step 575

**แบบฝึกหัดที่ 6:** เปิด Audience Overlap Tool ใน Business Manager เช็ก Custom Audience/Lookalike ที่มีอยู่ในบัญชีจริงของคุณอย่างน้อย 3 คู่ บันทึก % Overlap และตัดสินใจว่าคู่ไหนควร Exclude กันเพื่อลด Internal Competition

**แบบฝึกหัดที่ 7:** เขียนรายการความเสี่ยงเชิง Correlation (Pixel, Ad Account, Payment Method, Creative) ของธุรกิจคุณเอง พร้อมแผนสำรองสำหรับแต่ละข้อตามตารางใน Step 578

## สรุปและเชื่อมไปยัง Part ถัดไป

ทบทวนภาพรวมทั้ง Part นี้อีกครั้ง: Vertical Scaling ใช้ 20% Rule เพื่อเพิ่มงบอย่างปลอดภัยในสิ่งที่พิสูจน์แล้วว่าดี Horizontal Scaling ใช้เพื่อขยายพื้นที่และค้นหา Winner ตัวใหม่อยู่เสมอ Core-Satellite Model ผสมทั้งสองแนวทางเข้าด้วยกันอย่างเป็นระบบ ในขณะที่การจัดการความเสี่ยงทั้งเชิงปริมาณ (ไม่ Scale 100% เข้า Ad Set เดียว) และเชิง Correlation (ไม่ให้ทุก Core เสี่ยงพร้อมกันจากปัจจัยเดียว) คือเกราะป้องกันที่ทำให้ธุรกิจไม่ล้มทั้งกระดานเมื่อเกิดปัญหาไม่คาดคิด

การ Scale ที่ดีไม่ใช่การกดเพิ่มงบให้เร็วที่สุด แต่คือระบบที่มีวินัย — ใช้ Vertical Scaling ตาม 20% Rule เพื่อความปลอดภัย ควบคู่กับ Horizontal Scaling เพื่อค้นหา Winner ตัวใหม่อยู่เสมอ พร้อมกระจายความเสี่ยงไม่ให้ธุรกิจพึ่งพา Ad Set เดียวมากเกินไป

Part ถัดไปจะลงรายละเอียดเรื่อง **การควบคุมงบในระดับโครงสร้าง** ให้ลึกกว่าที่เคยเรียนใน Part 018 — **Part 059: Budget Optimization (CBO/ABO) และ Bid Cap** จะพาไปดูว่าเมื่อ Scale ไปถึงงบระดับสูงแล้ว ควรจัดโครงสร้าง CBO/ABO และ Bid Strategy อย่างไรให้ป้องกัน Ad Set สำคัญไม่ถูก "อดงบ" และควบคุม CPA ได้แม่นยำขึ้นในระดับที่ซับซ้อนกว่าช่วงเริ่มต้น สิ่งที่คุณเรียนรู้เรื่อง Core-Satellite Model ในบทนี้จะเชื่อมโยงตรงกับการเลือกใช้ CBO หรือ ABO ให้เหมาะกับบทบาทของ Ad Set แต่ละกลุ่มในบทต่อไป
