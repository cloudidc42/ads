## Step 581: ทบทวน CBO vs ABO ที่ระดับ Scale สูง

### ปัญหาที่ไม่ปรากฏตอนงบน้อย แต่ปรากฏชัดตอนงบสูง

ตอนงบ 1,000-2,000 บาท/วัน กับ 2-3 Ad Set ปัญหาการกระจายงบของ CBO มักไม่รุนแรงมาก เพราะมี "ตัวเลือก" ให้ระบบจัดสรรน้อย แต่พอ Scale ไปถึงงบ 15,000-30,000 บาท/วัน พร้อม Ad Set 8-15 กลุ่ม (ผสม Core และ Satellite ตามที่เรียนใน Part 058) ปัญหาการกระจายงบจะซับซ้อนขึ้นมาก และผลกระทบจากการกระจายผิดพลาดก็มีขนาดใหญ่ขึ้นตามงบ

### ตารางเปรียบเทียบ CBO/ABO ที่ระดับ Scale สูง (เพิ่มเติมจาก Part 018)

| ประเด็น | CBO ที่ Scale สูง | ABO ที่ Scale สูง |
|---|---|---|
| ความซับซ้อนในการติดตาม | ต่ำ (ระบบจัดการอัตโนมัติ) แต่ต้องเฝ้าดูว่าเทงบไปผิดที่หรือไม่ | สูงมาก ต้องเช็ก Ad Set 8-15 กลุ่มด้วยตัวเองสม่ำเสมอ |
| ความเสี่ยง Ad Set ใหม่ไม่ได้งบทดสอบ | สูงมาก เพราะ Ad Set ที่มีข้อมูลเก่าจะได้เปรียบเสมอ | ต่ำ เพราะควบคุมงบราย Ad Set ได้ตรง |
| ความเสี่ยง Internal Competition (Ad Set แข่งกันเอง) | สูง ถ้า Ad Set มีจำนวนมากและ Audience ทับซ้อน | ต่ำกว่า เพราะงบถูกกันไว้ตายตัว ไม่แย่งกันแบบ Real-time |
| ความเร็วในการตอบสนองต่อ Winner ใหม่ | เร็วมาก (นาทีถึงชั่วโมง) | ช้ากว่า (ต้องรอคนเข้าไปปรับ) |
| ความเหมาะสมกับ Core-Satellite Model | ควรแยก Campaign CBO ต่างหากสำหรับ Core และ Satellite ไม่ปนกัน | เหมาะกับ Satellite ที่ต้องการงบทดสอบยุติธรรม |

### แนวทางที่แนะนำที่ระดับ Scale สูง: แยก Campaign ตามบทบาทอย่างเคร่งครัด

เมื่องบโตขึ้นมาก ไม่ควรยัด Core และ Satellite ไว้ใน CBO Campaign เดียวกันอีกต่อไป (ต่างจากตอนงบน้อยที่อาจพอทำได้) ควรแยกเป็น:

- **CBO Campaign "Core"** — รวม Ad Set ที่พิสูจน์แล้วว่าชนะทั้งหมด ให้ระบบกระจายงบระหว่าง Core ด้วยกันเองได้ (เพราะทุกตัวมีคุณภาพใกล้เคียงกันแล้ว)
- **ABO Campaign "Satellite"** — แต่ละ Ad Set ทดสอบได้งบการันตีเท่ากัน เพื่อเทียบกันอย่างเป็นธรรมก่อนตัดสินใจว่าตัวไหนควรถูกโปรโมทเป็น Core

### ตัวอย่างตัวเลขจริงแสดงผลต่างระหว่างการแยก Campaign กับการยัดรวม

ธุรกิจ E-commerce งบรวม 12,000 บาท/วัน มี Ad Set 6 กลุ่ม (3 Core + 3 Satellite) ทดลองเปรียบเทียบสองโครงสร้าง:

| โครงสร้าง | Cost per Purchase เฉลี่ยรวม | Satellite ที่จบ Learning Phase ได้ | เวลาที่ใช้ค้นพบ Winner ใหม่ |
|---|---|---|---|
| CBO เดียวรวมทั้ง 6 กลุ่ม | 175 บาท | 0 จาก 3 | ไม่พบเลยใน 21 วัน |
| แยก CBO Core (3 กลุ่ม) + ABO Satellite (3 กลุ่ม) | 138 บาท | 2 จาก 3 | พบ 2 ตัวใน 21 วัน |

ตัวเลขนี้ตอกย้ำหลักการใน Step 581 — การแยก Campaign ตามบทบาทไม่ใช่แค่ทฤษฎี แต่ให้ผลต่างที่จับต้องได้ทั้งในแง่ต้นทุนและความสามารถในการค้นพบ Winner ใหม่ต่อเนื่อง

### ข้อผิดพลาดที่พบบ่อย

- ใช้ CBO เดียวครอบคลุมทั้ง Core และ Satellite พร้อมกันที่งบสูง ทำให้ Satellite ใหม่ไม่มีโอกาสได้งบพอจะพิสูจน์ตัวเองเลยเพราะ Core ที่มีข้อมูลเก่าได้เปรียบเสมอ
- เปลี่ยนจาก ABO เป็น CBO (หรือกลับกัน) กลางทางตอนงบสูงโดยไม่ทันคิดว่าจะรีเซ็ต Learning Phase ทุก Ad Set ในแคมเปญนั้นพร้อมกัน ความเสียหายจะมากกว่าตอนงบน้อยมาก

## Step 582: Bid Cap Strategy สำหรับควบคุม CPA ที่ระดับ Scale

### ทำไม Bid Cap สำคัญขึ้นเมื่อ Scale

ตอนงบน้อย การใช้ Lowest Cost มักโอเคเพราะความเสียหายจากความผันผวนของ CPA มีขนาดเล็ก แต่ตอนงบสูง (เช่น 20,000 บาท/วัน) ความผันผวนแบบเดียวกันแปลเป็นเงินก้อนใหญ่กว่ามาก — Bid Cap คือเครื่องมือควบคุมที่ละเอียดที่สุดในการจำกัดว่า "จะไม่ยอมจ่ายแพงกว่านี้ในแต่ละ Auction เด็ดขาด"

### วิธีคำนวณ Bid Cap จากข้อมูลจริง

หลักการคือใช้ข้อมูล **Cost per Result เฉลี่ยของ Ad Set ที่พิสูจน์แล้วว่าดี** เป็นฐาน แล้วตั้ง Bid Cap ให้สูงกว่าค่าเฉลี่ยเล็กน้อยเพื่อให้ระบบยังมีที่ยืนในการแข่ง Auction ได้ ไม่ใช่ตั้งเท่ากับ Break-even ทันที

```
Bid Cap ที่แนะนำ = Cost per Result เฉลี่ย 14 วันล่าสุด x 1.15-1.25
```

### ตัวอย่างตัวเลขจริง

Ad Set หนึ่งมี Cost per Purchase เฉลี่ย 14 วันล่าสุดอยู่ที่ 140 บาท (Break-even 220 บาท):

```
Bid Cap แนะนำ = 140 x 1.20 = 168 บาท
```

ตั้ง Bid Cap ที่ 168 บาท ให้ระบบมีช่องว่างพอจะแข่ง Auction ในวันที่ราคาแพงกว่าปกติเล็กน้อย โดยไม่ให้หลุดไปแพงเกินจนไม่ Break-even

### ผลลัพธ์เปรียบเทียบ Lowest Cost vs Bid Cap ที่งบสูง

Ad Set งบ 15,000 บาท/วัน รัน 10 วัน:

| ตัวชี้วัด | Lowest Cost | Bid Cap (168 บาท) |
|---|---|---|
| Amount Spent รวม 10 วัน | 150,000 บาท (ใช้เต็ม) | 132,000 บาท (88% เพราะบางช่วงประมูลไม่ทันเพดาน) |
| Purchases รวม | 780 | 740 |
| Cost per Purchase เฉลี่ย | 192 บาท | 178 บาท |
| Cost per Purchase สูงสุดในวันที่แพงที่สุด | 310 บาท | 195 บาท |
| ความผันผวน (ส่วนต่างวันแพงสุด-ถูกสุด) | 195 บาท | 62 บาท |

Bid Cap ควบคุมความผันผวนได้ดีกว่ามากในระดับงบสูง แม้ได้ Purchase น้อยกว่าเล็กน้อย (740 vs 780) แต่ Cost per Purchase เฉลี่ยถูกกว่าและมีความเสถียรสูงกว่าอย่างชัดเจน — ที่ระดับงบสูง ความเสถียรแบบนี้มีค่ามากเพราะลดความเสี่ยงของการขาดทุนก้อนใหญ่ในวันที่ Auction แพงผิดปกติ

### ขั้นตอนการปรับ Bid Cap แบบค่อยเป็นค่อยไปเมื่อ Scale งบต่อเนื่อง

Bid Cap ที่ตั้งไว้ตอนงบ 2,000 บาท/วัน อาจไม่เหมาะสมอีกต่อไปเมื่อ Scale ไปถึง 15,000 บาท/วัน เพราะ Auction ที่ต้องแข่งด้วยงบสูงมักเจอคู่แข่งกลุ่มที่ Bid สูงกว่าเป็นระยะๆ (Auction Diversity เพิ่มขึ้นตามขนาดงบ) แนะนำให้ทบทวน Bid Cap ทุกครั้งที่ Vertical Scale ผ่านไปแล้ว 2-3 รอบตาม 20% Rule (ทบทวน Part 058):

| รอบการ Scale | งบ/วัน | Cost per Result เฉลี่ย 7 วันล่าสุด | Bid Cap ที่ควรปรับ |
|---|---|---|---|
| เริ่มต้น | 2,000 บาท | 140 บาท | 168 บาท (x1.2) |
| หลัง Scale รอบที่ 3 | 3,456 บาท | 152 บาท | 178 บาท (x1.17) |
| หลัง Scale รอบที่ 6 | 5,972 บาท | 165 บาท | 195 บาท (x1.18) |

หลักการคือปรับ Bid Cap ตาม Cost per Result เฉลี่ยที่เปลี่ยนไปจริง ไม่ใช่ยึดติดกับตัวเลขเดิมตลอดไป

### ข้อผิดพลาดที่พบบ่อย

- ตั้ง Bid Cap โดยใช้ข้อมูล Cost per Result จากช่วง Learning Phase ที่ยังไม่นิ่ง ทำให้ตั้งเพดานผิดตั้งแต่ต้น
- ไม่ปรับ Bid Cap ตามฤดูกาล (เช่น ตั้งเพดานไว้ตายตัวทั้งปี ทั้งที่ช่วงไฮซีซัน Auction แพงขึ้นตามธรรมชาติ ควรขยับ Bid Cap ขึ้นชั่วคราวในช่วงนั้น)
- ตั้ง Bid Cap ต่ำเกินไปโดยหวังบีบต้นทุน ทำให้แคมเปญที่งบสูงใช้เงินไม่หมดเลย เสียโอกาสจำนวนมาก
- ไม่ทบทวน Bid Cap เลยหลังจาก Scale งบไปหลายรอบ ทำให้เพดานเดิมที่เหมาะกับงบน้อยกลายเป็นข้อจำกัดที่ฉุดรั้งการเติบโตที่งบสูง

## Step 583: Cost Cap vs Bid Cap — ความแตกต่างเชิงกลไกพร้อมตัวอย่างตัวเลข

### ความแตกต่างเชิงกลไกที่แท้จริง

**Cost Cap** ควบคุม **ค่าเฉลี่ย** ของต้นทุนต่อผลลัพธ์ทั้งหมด ระบบมีความยืดหยุ่นในการ "จ่ายแพงกว่าเพดานในบาง Auction" ตราบใดที่ค่าเฉลี่ยรวมยังไม่เกินเพดานที่ตั้งไว้ — เปรียบเหมือนงบประมาณครัวเรือนที่ยอมให้เดือนนี้ใช้เกินได้บ้างถ้าเดือนหน้าใช้น้อยลงชดเชย

**Bid Cap** ควบคุม **ราคาสูงสุดในแต่ละ Auction เดี่ยวๆ** อย่างเข้มงวด ไม่มีการยอมให้เกินแม้แต่ครั้งเดียว ระบบจะไม่เข้าประมูลเลยถ้าราคาที่ต้องจ่ายเกินเพดานที่ตั้งไว้ — เปรียบเหมือนการตั้งเพดานราคาสูงสุดที่ยอมจ่ายในการประมูลของแต่ละชิ้น ไม่มีข้อยกเว้น

### ตัวอย่างตัวเลขเปรียบเทียบกลไกแบบละเอียด

สมมติทั้งสองแบบตั้งเพดานที่ 150 บาท และมี Auction เกิดขึ้น 5 ครั้งในหนึ่งวัน:

| Auction ครั้งที่ | ราคาที่ต้องจ่ายจริงถ้าจะชนะ | Cost Cap (150 บาท) ทำอะไร | Bid Cap (150 บาท) ทำอะไร |
|---|---|---|---|
| 1 | 100 บาท | เข้าประมูล ชนะ (ถูกกว่าเพดาน) | เข้าประมูล ชนะ (ถูกกว่าเพดาน) |
| 2 | 130 บาท | เข้าประมูล ชนะ | เข้าประมูล ชนะ |
| 3 | 180 บาท | อาจเข้าประมูลและจ่าย 180 บาท (เกินเพดานเดี่ยว) เพราะเฉลี่ยรวมยังไม่เกิน | **ไม่เข้าประมูลเลย** เพราะเกินเพดานเดี่ยวที่ตั้งไว้ |
| 4 | 90 บาท | เข้าประมูล ชนะ | เข้าประมูล ชนะ |
| 5 | 160 บาท | อาจเข้าประมูลถ้าเฉลี่ยรวมยังไม่เกิน 150 บาท | ไม่เข้าประมูล (เกินเพดานเดี่ยว) |

**ผลลัพธ์ Cost Cap:** ชนะ 5 ครั้งจาก 5 (รวม 660 บาท ÷ 5 = 132 บาทเฉลี่ย ยังต่ำกว่าเพดาน 150 บาท)
**ผลลัพธ์ Bid Cap:** ชนะแค่ 3 ครั้งจาก 5 (รวม 320 บาท ÷ 3 = 106.67 บาทเฉลี่ย ถูกกว่ามาก แต่ได้ผลลัพธ์น้อยกว่า)

### สรุปเมื่อไหร่ควรใช้แบบไหน

| สถานการณ์ | แนะนำ |
|---|---|
| ต้องการ Volume สูงสุดภายใต้ต้นทุนเฉลี่ยที่ยอมรับได้ | Cost Cap |
| ต้องการควบคุมต้นทุนสูงสุดแบบเข้มงวดที่สุด ยอมได้ Volume น้อยลง | Bid Cap |
| งบสูงมาก ธุรกิจอ่อนไหวต่อความผันผวนของ Cash Flow | Bid Cap |
| ธุรกิจที่ Margin สูง ยอมรับความผันผวนได้ เน้น Volume | Cost Cap |
| มีข้อมูล Auction ในอดีตมากพอจะประเมินราคาที่เหมาะสม | Bid Cap (ต้องการความรู้เชิงลึกกว่า) |

### ข้อผิดพลาดที่พบบ่อย

- เข้าใจว่า Cost Cap และ Bid Cap ทำงานเหมือนกันเพียงแต่ชื่อต่างกัน ทำให้เลือกใช้ผิดสถานการณ์
- ใช้ Bid Cap โดยไม่มีข้อมูล Auction มาก่อน ทำให้ตั้งเพดานผิดจนแคมเปญไม่วิ่งเลย (ปัญหาที่พบบ่อยที่สุดของ Bid Cap)

### แนวทางไฮบริด: เริ่มด้วย Cost Cap ก่อนขยับไป Bid Cap

สำหรับธุรกิจที่ Scale ไปถึงงบสูงและต้องการควบคุมที่ละเอียดที่สุด แนวทางที่ปลอดภัยคือไม่กระโดดไปใช้ Bid Cap ทันที แต่ไล่ระดับความเข้มงวดขึ้นทีละขั้น:

| ระยะ | Bid Strategy | เหตุผล |
|---|---|---|
| ระยะที่ 1 (สัปดาห์ 1-2) | Lowest Cost | เก็บข้อมูล Benchmark เริ่มต้น ยังไม่มีข้อมูลพอตั้งเพดานใดๆ |
| ระยะที่ 2 (สัปดาห์ 3-4) | Cost Cap (ตั้งจาก Benchmark ที่เก็บได้) | เริ่มควบคุมต้นทุนเฉลี่ย ยังยอมให้ระบบมีความยืดหยุ่น |
| ระยะที่ 3 (เดือนที่ 2 เป็นต้นไป, งบสูงและเสถียรแล้ว) | Bid Cap (ตั้งจาก Cost per Result ภายใต้ Cost Cap) | ควบคุมความผันผวนละเอียดที่สุดเมื่อมีข้อมูลมากพอ |

การไล่ระดับแบบนี้ลดความเสี่ยงที่แคมเปญจะ "ไม่วิ่งเลย" จากการตั้งเพดานผิดตั้งแต่ต้น เพราะแต่ละระยะสร้างข้อมูลให้ระยะต่อไปใช้ตั้งเพดานได้แม่นยำขึ้น

## Step 584: Advantage Campaign Budget — เมื่อไหร่ช่วย เมื่อไหร่ทำร้ายการกระจายงบ

### กลไกภายในที่ต้องเข้าใจลึกกว่า Part 018

Advantage Campaign Budget (ชื่อปัจจุบันของ CBO) ใช้หลักการ "Predicted Marginal Return" — ระบบพยายามคาดการณ์ว่าถ้าเพิ่มเงิน 1 บาทให้ Ad Set ไหน จะได้ผลตอบแทนส่วนเพิ่มมากที่สุด แล้วเทงบไปทางนั้น การคาดการณ์นี้อ้างอิงจากข้อมูลสะสมของแต่ละ Ad Set ทำให้ Ad Set ที่มีข้อมูลมากกว่า (อายุนานกว่า) มักได้เปรียบเชิงระบบเหนือ Ad Set ใหม่ที่ยังไม่มีข้อมูลมากพอ

### เมื่อไหร่ Advantage Campaign Budget ช่วยได้ดี

- Ad Set ทุกกลุ่มมีบทบาทเดียวกัน (เช่น ทดสอบ Creative หลายตัวในกลุ่มเป้าหมายเดียวกัน)
- ทุก Ad Set มีอายุ/ข้อมูลสะสมใกล้เคียงกัน ไม่มีตัวไหนได้เปรียบจากข้อมูลเก่ามากเกินไป
- ต้องการความเร็วในการตัดสินใจที่มนุษย์ทำไม่ได้ทัน (Ad Set จำนวนมาก เปลี่ยนแปลงเร็ว)

### เมื่อไหร่ Advantage Campaign Budget ทำร้ายการกระจายงบ

- มี Ad Set ที่มีบทบาทต่างกันสิ้นเชิงปนกัน (Cold Prospecting vs Retargeting) — ระบบจะเทงบไปที่ Retargeting เกือบหมดเพราะ CPA ถูกกว่าตามธรรมชาติ ทำให้ไม่มีลูกค้าใหม่เข้าระบบต่อเนื่อง
- มี Ad Set ใหม่ที่ยังไม่มีข้อมูลปนกับ Ad Set เก่าที่มีข้อมูลสะสมมาก — Ad Set ใหม่จะไม่ได้งบพอพิสูจน์ตัวเองเลย แม้จริงๆอาจมีศักยภาพดีกว่า
- Audience ของ Ad Set ต่างๆ Overlap กันมาก ทำให้ระบบสับสนว่าผลลัพธ์มาจาก Ad Set ไหนกันแน่ (Attribution Confusion ภายในระบบ)

### ตัวอย่างตัวเลขแสดงปัญหา "Ad Set ใหม่ไม่ได้งบ"

CBO Campaign มี Ad Set เก่าอายุ 60 วัน กับ Ad Set ใหม่อายุ 2 วัน งบรวม 8,000 บาท/วัน:

| Ad Set | อายุ | Cost per Purchase สะสม | งบที่ได้รับจริงวันที่ 3 หลังเพิ่ม Ad Set ใหม่ |
|---|---|---|---|
| Ad Set เก่า (มีข้อมูล 60 วัน) | 60 วัน | 130 บาท | 7,400 บาท (92.5%) |
| Ad Set ใหม่ (มีข้อมูลแค่ 2 วัน) | 2 วัน | 210 บาท (ยัง Learning) | 600 บาท (7.5%) |

Ad Set ใหม่ได้งบเพียง 600 บาท/วัน ซึ่งอาจไม่พอให้จบ Learning Phase เลย (ทบทวน Minimum Budget ใน Part 018) ทำให้ไม่มีโอกาสพิสูจน์ว่าจริงๆแล้วมันอาจดีกว่า Ad Set เก่าถ้าได้งบทดสอบเพียงพอ

### วิธีแก้ปัญหานี้

ตั้ง **Minimum Budget ต่อ Ad Set** ใน CBO (Meta อนุญาตให้กำหนด Cost per Result Goal หรือ Minimum Spend ในบางรูปแบบ) หรือทางที่ตรงกว่าคือย้าย Ad Set ใหม่ไปทดสอบใน ABO Campaign ต่างหากก่อน (ตามที่แนะนำใน Step 581) จนกว่าจะพิสูจน์ตัวเองได้ แล้วค่อยย้ายเข้า CBO Core

### ข้อผิดพลาดที่พบบ่อย

- เพิ่ม Ad Set ใหม่เข้า CBO ที่มี Ad Set เก่าซึ่งมีข้อมูลสะสมมากอยู่แล้ว โดยคาดหวังให้แข่งกันอย่างเป็นธรรม
- ไม่เข้าใจว่า CBO "ไม่ได้เก่งกว่ามนุษย์เสมอไป" ในทุกสถานการณ์ — มันเก่งเรื่องการตัดสินใจเร็วจากข้อมูลที่มี แต่ไม่รู้ "เจตนาเชิงกลยุทธ์" ของธุรกิจ (เช่น ทำไมต้องรักษา Cold Prospecting ไว้แม้ CPA แพงกว่า)

### เทคนิคการใช้ Cost per Result Goal เพื่อชี้นำการกระจายงบของ CBO

Meta อนุญาตให้ตั้ง "Cost per Result Goal" ราย Ad Set ภายใน CBO Campaign ได้ในบางรูปแบบ ซึ่งเป็นเครื่องมือชี้นำทางอ้อมที่ช่วยลดปัญหาการกระจายงบผิดที่ได้บางส่วน — การตั้งค่านี้บอกระบบว่า "Ad Set นี้ยอมรับต้นทุนสูงกว่าปกติได้ในระดับหนึ่ง" ทำให้ Ad Set ที่มีบทบาทเชิงกลยุทธ์ (เช่น Cold Prospecting) ไม่ถูกตัดงบจนเหลือ 0 ง่ายเกินไป แม้จะไม่สามารถการันตีงบตายตัวเท่า ABO ก็ตาม

### ข้อผิดพลาดที่พบบ่อยเพิ่มเติม

- ไม่ใช้ Cost per Result Goal เลยทั้งที่มี Ad Set ที่มีบทบาทเชิงกลยุทธ์ต่างกันปนอยู่ใน CBO เดียวกัน ทำให้พลาดเครื่องมือชี้นำที่ช่วยลดปัญหาได้บางส่วน
- ตั้ง Cost per Result Goal สูงเกินจริงจนไม่ต่างจากไม่ตั้งเลย หรือต่ำเกินจนแคมเปญไม่วิ่งในกลุ่มนั้น

## Step 585: Minimum Spend Threshold ต่อ Ad Set เพื่อป้องกัน Starvation

### Starvation คืออะไร

Ad Set "Starvation" คือสถานการณ์ที่ Ad Set หนึ่งได้งบน้อยเกินไปจนไม่สามารถสะสม Optimization Events ได้ทันเวลา ทำให้ติดอยู่ใน Learning Limited ตลอดไป หรือแม้จะจบ Learning ได้ก็ใช้เวลานานเกินจำเป็น เสียโอกาสไปมาก — มักเกิดในโครงสร้าง CBO ที่มี Ad Set จำนวนมากแข่งกัน หรือ ABO ที่ตั้งงบผิดสัดส่วน

### วิธีคำนวณ Minimum Spend Threshold

ใช้สูตรเดียวกับ Minimum Budget ใน Part 018 Step 177 แต่ปรับให้เข้ากับสถานการณ์ Multi-Ad-Set:

```
Minimum Spend Threshold ต่อ Ad Set = (50 Events ÷ 7 วัน) x Cost per Result โดยประมาณของ Ad Set นั้น
```

### ตัวอย่างการคำนวณสำหรับ CBO ที่มี 5 Ad Set

| Ad Set | Cost per Result ประมาณ | Minimum Spend Threshold/วัน |
|---|---|---|
| Lookalike 1% | 130 บาท | (50÷7) x 130 = 928 บาท |
| Lookalike 2-5% | 180 บาท | (50÷7) x 180 = 1,286 บาท |
| Interest A | 220 บาท | (50÷7) x 220 = 1,571 บาท |
| Interest B | 250 บาท | (50÷7) x 250 = 1,786 บาท |
| Retargeting | 90 บาท | (50÷7) x 90 = 643 บาท |
| **รวม Minimum Spend ที่ต้องการทั้งแคมเปญ** | | **6,214 บาท/วัน** |

ถ้า CBO Campaign นี้ตั้งงบรวมไว้ต่ำกว่า 6,214 บาท/วัน มีความเสี่ยงสูงที่บาง Ad Set จะเกิด Starvation แน่นอน เพราะงบไม่พอให้ทุกกลุ่มสะสม Event ถึงเกณฑ์พร้อมกัน — นี่คือเหตุผลที่การเพิ่ม Ad Set เข้า CBO มากเกินไปโดยไม่เพิ่มงบตามสัดส่วนคือกับดักใหญ่

### กฎง่ายๆที่ใช้จำได้ทันที

```
งบ CBO ขั้นต่ำที่ควรตั้ง = ผลรวม Minimum Spend Threshold ของทุก Ad Set ในแคมเปญนั้น
```

ถ้างบที่มีจริงน้อยกว่าผลรวมนี้ ควรลดจำนวน Ad Set ลง ไม่ใช่เพิ่มงบรวมแบบไม่มีเหตุผล (ถ้าธุรกิจมีงบจำกัด)

### ข้อผิดพลาดที่พบบ่อย

- เพิ่ม Ad Set เข้า CBO เรื่อยๆเพื่อ "ทดสอบให้ครบทุกไอเดีย" โดยไม่คำนวณ Minimum Spend Threshold รวมก่อน ทำให้ทุก Ad Set อดงบพร้อมกัน
- ไม่แยก Cost per Result ประมาณการระหว่าง Ad Set Cold กับ Warm/Hot ทำให้คำนวณ Threshold ผิดพลาด (Cold มักต้องการ Threshold สูงกว่าเพราะ Cost per Result แพงกว่าธรรมชาติ)

### ผลกระทบของ Starvation ที่มองไม่เห็นในตัวเลขเฉลี่ยรวม

ปัญหา Starvation อันตรายเพราะมันมัก "ซ่อน" อยู่หลังตัวเลขเฉลี่ยรวมของ Campaign ที่ดูปกติ เนื่องจาก Ad Set ที่ทำงานได้ดี (ไม่ Starve) ยังคงดึงตัวเลขเฉลี่ยให้ดูดีอยู่ ทำให้ปัญหาถูกมองข้ามไปเรื่อยๆ จนกว่าจะมีคนเข้าไปเช็กระดับ Ad Set โดยตรง (ทบทวนความสำคัญของการดู Breakdown ระดับ Ad Set ใน Part 056)

| ระดับที่ดู | ตัวเลขที่เห็น | ปัญหาที่ซ่อนอยู่ |
|---|---|---|
| Campaign (เฉลี่ยรวม) | Cost per Purchase 145 บาท (ดูโอเค) | มองไม่เห็นว่า 2 ใน 5 Ad Set กำลัง Starve |
| Ad Set (แยกราย) | Ad Set A: 95 บาท, Ad Set B: 110 บาท, Ad Set C-E: Learning Limited ไม่มีผลลัพธ์เลย | เห็นชัดว่า 60% ของ Ad Set ไม่ได้ทำงานเลย |

## Step 586: สัญญาณ Budget Reallocation ที่ต้องจับตา

### สัญญาณที่บอกว่าควรย้ายงบระหว่าง Ad Set

**1. Cost per Result ต่างกันมากระหว่าง Ad Set ต่อเนื่อง 5+ วัน** — ถ้า Ad Set A ทำได้ 100 บาท ต่อเนื่อง ในขณะที่ Ad Set B ทำได้ 350 บาทต่อเนื่อง เป็นสัญญาณชัดว่าควรย้ายงบจาก B ไป A (ยกเว้นถ้า B มีบทบาทเชิงกลยุทธ์ที่ต้องรักษาไว้ เช่น Cold Prospecting)

**2. Delivery Status "Learning Limited" ต่อเนื่องเกิน 7 วัน** — สัญญาณว่า Ad Set นั้นต้องการงบเพิ่ม หรือควรถูกรวมเข้ากับ Ad Set อื่นที่ Audience คล้ายกัน

**3. Frequency พุ่งสูงในบาง Ad Set ขณะที่งบอื่นยังมี Reach เหลือ** — สัญญาณว่าควรลดงบ Ad Set ที่ Saturate แล้วย้ายไปยัง Ad Set ที่ยังมีพื้นที่ให้ขยาย

**4. Quality/Engagement/Conversion Ranking ตกลงต่อเนื่อง** — สัญญาณว่า Ad Set นั้นกำลังเสื่อมประสิทธิภาพ ควรลดงบและเพิ่มให้ Ad Set ที่ Ranking ดีกว่า

### ตารางสัญญาณและ Action ที่แนะนำ

| สัญญาณ | Action แนะนำ |
|---|---|
| Cost per Result ต่างกัน 2x+ ต่อเนื่อง 5 วัน (ไม่มีบทบาทเชิงกลยุทธ์ต่างกัน) | ย้ายงบจาก Ad Set แพงไป Ad Set ถูก ตาม 20% Rule |
| Learning Limited ต่อเนื่อง 7+ วัน | เพิ่มงบหรือรวม Ad Set กับกลุ่มที่ Audience ใกล้เคียง |
| Frequency สูงกว่า Benchmark ต่อเนื่อง 5+ วัน | ลดงบ 10-20% ย้ายไปยัง Ad Set ที่ Reach ยังเติบโตได้ |
| Ranking ตกจาก Above Average เป็น Below Average | ลดงบและวางแผนรีเฟรชครีเอทีฟ ก่อนย้ายงบกลับเมื่อ Ranking ฟื้น |

### ข้อผิดพลาดที่พบบ่อย

- ย้ายงบจาก Ad Set ที่ CPA แพงกว่าไปทันทีโดยไม่เช็กว่า Ad Set นั้นมีบทบาทเชิงกลยุทธ์ (เช่น Cold Prospecting ที่ต้องรักษาไว้แม้ CPA แพงกว่า Retargeting)
- ตอบสนองต่อสัญญาณเร็วเกินไป (1-2 วัน) โดยไม่รอดูว่าเป็นความผันผวนปกติหรือ Trend จริง

## Step 587: ใช้ Automated Rules ปรับงบอัตโนมัติ

### ทำไมต้องใช้ Automated Rules

ที่ระดับ Scale สูงพร้อม Ad Set จำนวนมาก การเฝ้าจอปรับงบด้วยมือทุกวันไม่ยั่งยืน — Automated Rules ช่วยให้ระบบตรวจสอบและปรับงบ/หยุดโฆษณาให้อัตโนมัติตามเงื่อนไขที่ตั้งไว้ ตลอด 24 ชั่วโมง (รายละเอียดเชิงลึกเรื่อง Automation ทั้งหมดจะอยู่ใน Part 063 แต่ในที่นี่จะโฟกัสเฉพาะการใช้กับ Budget)

### ตัวอย่าง Automated Rules สำหรับ Budget Management

**Rule 1: เพิ่มงบอัตโนมัติเมื่อ Ad Set ทำได้ดีต่อเนื่อง**
- เงื่อนไข: Cost per Purchase ต่ำกว่า 150 บาท ต่อเนื่อง 3 วัน AND Frequency ต่ำกว่า 3.0
- Action: เพิ่ม Budget 15% (ตั้งต่ำกว่า 20% เพื่อความปลอดภัยเผื่อ Rule รันถี่กว่าที่คาด)

**Rule 2: ลดงบอัตโนมัติเมื่อสัญญาณ Saturation ปรากฏ**
- เงื่อนไข: Frequency สูงกว่า 5.0 AND Cost per Purchase สูงกว่า 250 บาท ต่อเนื่อง 2 วัน
- Action: ลด Budget 20% และส่ง Notification เตือนให้เข้าไปพิจารณาต่อ

**Rule 3: หยุด Ad Set อัตโนมัติเมื่อผลลัพธ์แย่ชัดเจน**
- เงื่อนไข: Amount Spent เกิน 1,000 บาท AND Purchases = 0
- Action: Pause Ad Set + ส่ง Notification (ไม่ควร Pause แบบไม่มีการแจ้งเตือน เพราะอาจ Pause ผิดจังหวะ Learning Phase)

**Rule 4: แจ้งเตือนเมื่อ Ranking ตกลง**
- เงื่อนไข: Quality Ranking = "Below Average (Bottom 20%)"
- Action: ส่ง Notification เท่านั้น (ไม่ให้ระบบปรับงบอัตโนมัติในเรื่องที่ต้องใช้วิจารณญาณของมนุษย์ประกอบ)

### ตารางสรุปหลักการตั้ง Automated Rules ที่ปลอดภัย

| หลักการ | เหตุผล |
|---|---|
| ตั้ง % การเพิ่ม/ลดงบให้ต่ำกว่า 20% Rule เล็กน้อย (เช่น 15%) | เผื่อกรณี Rule รันซ้ำเร็วกว่าที่คาด ป้องกันสะสมเกิน 20% ในช่วงเวลาสั้น |
| ใช้เงื่อนไขที่รวมหลายตัวชี้วัด ไม่ใช่ตัวเดียว | ลดโอกาส False Positive จากความผันผวนปกติ |
| ตั้ง Notification คู่กับ Action เสมอสำหรับ Rule ที่มีผลกระทบมาก | ให้มนุษย์ตรวจสอบย้อนหลังได้ ไม่ปล่อยระบบทำงานแบบไม่มีใครรู้ |
| ไม่ตั้ง Rule ที่ปรับ Ad Set ตัวเดียวกันจากหลาย Rule ที่ขัดแย้งกัน | ป้องกันระบบเพิ่มและลดงบสวนทางกันจนแคมเปญไม่นิ่ง |

### ข้อผิดพลาดที่พบบ่อย

- ตั้ง Rule ให้ Pause อัตโนมัติเร็วเกินไป (เช่น ใช้เงื่อนไขจากข้อมูลวันแรกที่ยัง Learning) ทำให้ Pause Ad Set ที่มีศักยภาพดีก่อนที่จะได้เห็นผลจริง
- ตั้ง Rule เพิ่มงบแบบไม่มีเพดานสูงสุด (Maximum Budget) ทำให้ในกรณีที่ Metric ผิดปกติ (เช่น Bug การรายงาน) ระบบเพิ่มงบไปเรื่อยๆโดยไม่มีการควบคุม

## Step 588: ข้อผิดพลาด CBO ที่พบบ่อยที่สุด — Ad Set มากเกินไปแข่งกันเอง

### ปัญหาคลาสสิกที่พบในแคมเปญ Scale ขนาดใหญ่

เมื่อธุรกิจอยากทดสอบหลาย Audience หลายครีเอทีฟพร้อมกัน มักจะสร้าง Ad Set จำนวนมาก (10-20 กลุ่ม) ยัดใส่ CBO Campaign เดียว ด้วยความคิดว่า "ให้ AI เลือกเอง" — แต่ในความเป็นจริง เมื่อ Ad Set มากเกินไป เกิดปัญหาต่อไปนี้พร้อมกัน:

1. งบเฉลี่ยต่อ Ad Set น้อยเกินไปจนไม่มีตัวไหนจบ Learning Phase ได้เลย (Starvation ทั่วกระดาน)
2. ระบบสับสนเพราะ Audience Overlap กันเองหลายจุด ทำให้ Auction แข่งขันภายในสูงเกินจำเป็น (คุณแข่งกับตัวเอง)
3. ข้อมูลกระจัดกระจายเกินกว่าจะวิเคราะห์ได้ทันเวลา แม้แต่ AI เองก็ต้องใช้เวลานานกว่าจะหา Pattern ได้ชัดเจนเมื่อมีตัวแปรมากเกินไป

### ตัวอย่างตัวเลขแสดงปัญหาจริง

CBO Campaign งบ 6,000 บาท/วัน มี Ad Set 15 กลุ่ม:

```
งบเฉลี่ยต่อ Ad Set = 6,000 ÷ 15 = 400 บาท/วัน
```

400 บาท/วันต่อ Ad Set ต่ำกว่า Minimum Budget ที่แนะนำสำหรับ Sales Objective (800-1,500 บาทตาม Part 018) อย่างมาก — แม้ในทางเทคนิค CBO จะไม่ได้แบ่งเท่ากันทุกกลุ่ม แต่ในช่วงเริ่มต้นที่ยังไม่มีข้อมูลตัดสิน มันมักกระจายค่อนข้างเท่ากันก่อน ทำให้ทุกกลุ่มได้งบน้อยเกินไปพร้อมกันในช่วงสำคัญที่สุด (ช่วงเริ่ม Learning)

### จำนวน Ad Set ที่แนะนำต่อ CBO Campaign

| งบรวม Campaign/วัน | จำนวน Ad Set ที่แนะนำสูงสุด | เหตุผล |
|---|---|---|
| 1,000-3,000 บาท | 2-3 กลุ่ม | งบน้อย ต้องรวมศูนย์ให้พอจบ Learning Phase |
| 3,000-8,000 บาท | 3-5 กลุ่ม | เริ่มมีพื้นที่ให้ทดสอบมากขึ้นแต่ยังต้องระวัง |
| 8,000-20,000 บาท | 5-8 กลุ่ม | พอสำหรับ Core หลายตัวพร้อม Satellite บางส่วน |
| 20,000+ บาท | 6-10 กลุ่ม (แยก Campaign ตามบทบาทถ้าเกินนี้) | เกินกว่านี้ควรแยกเป็นหลาย Campaign ตามบทบาทดีกว่ายัดในเดียว |

### ข้อผิดพลาดที่พบบ่อย

- คิดว่า "ยิ่งมี Ad Set มาก AI ยิ่งมีตัวเลือกดี" ทั้งที่ความจริงตรงกันข้าม — AI ต้องการ "ข้อมูลสะสมเพียงพอต่อกลุ่ม" มากกว่า "จำนวนกลุ่มมาก"
- ไม่เคยรวม (Consolidate) Ad Set ที่ Audience คล้ายกันเข้าด้วยกัน ทำให้สะสมปัญหา Ad Set จำนวนมากเกินจำเป็นไปเรื่อยๆ

## Step 589: Case Study — ปรับโครงสร้าง CBO ที่พังให้กลับมาทำงานได้ดี

### สถานการณ์เริ่มต้น

ธุรกิจขายคอร์สออนไลน์ด้านการตลาดดิจิทัล มี CBO Campaign งบ 10,000 บาท/วัน มี Ad Set 12 กลุ่ม (ผสมทั้ง Cold Lookalike, Cold Interest 6 แบบ, Retargeting 3 แบบ, และ Creative Testing 2 กลุ่ม) รันมา 3 สัปดาห์ Cost per Lead เฉลี่ยรวมอยู่ที่ 285 บาท (Break-even 180 บาท) — ขาดทุนต่อเนื่อง

### ขั้นตอนที่ 1: ตรวจสอบ Delivery Status และการกระจายงบทุก Ad Set

| กลุ่ม Ad Set | จำนวนกลุ่ม | งบรวมที่ได้รับจริง | สถานะ |
|---|---|---|---|
| Cold Lookalike 1% | 1 | 4,200 บาท (42%) | Active, Cost/Lead 140 บาท |
| Cold Interest (6 แบบ) | 6 | 2,100 บาท (21%, เฉลี่ย 350/กลุ่ม) | ทุกกลุ่ม Learning Limited |
| Retargeting (3 แบบ) | 3 | 2,700 บาท (27%, เฉลี่ย 900/กลุ่ม) | Active, Cost/Lead 95 บาท |
| Creative Testing (2 แบบ) | 2 | 1,000 บาท (10%, เฉลี่ย 500/กลุ่ม) | Learning Limited ทั้งคู่ |

### ขั้นตอนที่ 2: วินิจฉัยปัญหา

พบว่า Cold Interest ทั้ง 6 กลุ่มติด Learning Limited พร้อมกันเพราะได้งบเฉลี่ยแค่ 350 บาท/วัน (ต่ำกว่า Minimum Budget ที่ควรได้มาก) ในขณะที่ Lookalike และ Retargeting ทำงานได้ดี แต่ตัวเลขเฉลี่ยรวมทั้งแคมเปญถูกฉุดลงมาจาก Cold Interest ทั้ง 6 กลุ่มที่ไม่เคยจบ Learning Phase เลยตลอด 3 สัปดาห์ (เผาเงินไปกับ Learning Limited โดยไม่ได้ผลลัพธ์คุ้มค่า)

### ขั้นตอนที่ 3: ปรับโครงสร้างใหม่

1. **รวม Cold Interest 6 กลุ่มเหลือ 2 กลุ่ม** — เลือกเฉพาะ Interest ที่มี Signal เริ่มดีที่สุด 2 ตัว รวม Audience ที่เหลือเข้าเป็น Interest กว้างขึ้น 1 กลุ่ม (ปิดกลุ่มที่ไม่มีสัญญาณอะไรเลย)
2. **แยก Campaign ใหม่:** CBO Campaign "Core" (Lookalike + Retargeting ที่พิสูจน์แล้ว) งบ 7,000 บาท และ ABO Campaign "Satellite" (Interest 2 กลุ่มที่เหลือ + Creative Testing 2 กลุ่ม) งบ 3,000 บาท แบ่งเท่ากันชัดเจนต่อกลุ่ม (750 บาท/กลุ่ม)
3. **ตั้ง Minimum Spend Threshold** ตามสูตร Step 585 สำหรับทุกกลุ่มใน Satellite เพื่อป้องกัน Starvation ซ้ำ

### ผลลัพธ์หลังปรับโครงสร้าง 14 วัน

| ตัวชี้วัด | ก่อนปรับ | หลังปรับ 14 วัน |
|---|---|---|
| Cost per Lead เฉลี่ยรวม | 285 บาท | 152 บาท |
| จำนวน Ad Set ที่ Learning Limited | 8 จาก 12 | 0 จาก 8 |
| Lead รวมต่อวัน | 35 | 61 |

### บทเรียนจาก Case Study นี้

การมี Ad Set จำนวนมากไม่ได้แปลว่า "ครอบคลุมทุกโอกาส" เสมอ — ถ้างบไม่พอรองรับทุกกลุ่มให้จบ Learning Phase การมี Ad Set น้อยกว่าแต่ได้งบเพียงพอต่อกลุ่มจะให้ผลลัพธ์ดีกว่าเสมอ การรวม (Consolidate) และแยก Campaign ตามบทบาทคือทางแก้ที่ตรงจุดที่สุดสำหรับปัญหา CBO ที่มี Ad Set มากเกินไป

## Step 590: Workshop — ตั้งค่า CBO Campaign พร้อม Minimum Spend Safeguard

### ขั้นตอนที่ต้องทำจริง

1. **กำหนดงบรวมของ CBO Campaign ที่จะสร้าง** — สมมติงบ 8,000 บาท/วัน
2. **ระบุ Ad Set ที่จะรวมเข้า Campaign นี้ (เฉพาะ Core ที่พิสูจน์แล้ว)** — ไม่เกิน 5 กลุ่มตามตาราง Step 588
3. **คำนวณ Minimum Spend Threshold ของแต่ละ Ad Set** ตามสูตร Step 585 โดยใช้ Cost per Result จริงหรือประมาณการ
4. **ตรวจสอบว่าผลรวม Minimum Spend Threshold ไม่เกินงบรวม** ถ้าเกิน ให้ลดจำนวน Ad Set หรือเพิ่มงบรวม
5. **เลือก Bid Strategy** ตามข้อมูลที่มี (Lowest Cost ถ้ายังไม่มี Benchmark มากพอ, Cost Cap/Bid Cap ถ้ามีข้อมูลแล้วตาม Step 582-583)
6. **สร้าง Automated Rule พื้นฐาน** อย่างน้อย 1 Rule แจ้งเตือนเมื่อ Ad Set ใดติด Learning Limited เกิน 7 วัน (ตาม Step 587)
7. **ตั้งตารางเช็ก Budget Reallocation Signal รายสัปดาห์** ตามสัญญาณใน Step 586

### แบบฟอร์มสำหรับ Workshop

| Ad Set | Cost per Result ประมาณการ | Minimum Spend Threshold/วัน | งบที่วางแผนให้ |
|---|---|---|---|
| | | | |
| | | | |
| | | | |
| **รวม** | | | |

ตรวจสอบว่า "รวม Minimum Spend Threshold" ≤ งบรวม CBO Campaign ที่ตั้งไว้ ถ้าไม่ผ่านเกณฑ์นี้ ห้ามเปิดแคมเปญจนกว่าจะปรับจำนวน Ad Set หรืองบให้สอดคล้องกัน

Part นี้ปิดจบชุดความรู้เรื่องการจัดการงบและ Bid Strategy ที่ระดับ Scale สูง — ตั้งแต่การเลือกโครงสร้าง CBO/ABO ที่เหมาะกับบทบาทของ Ad Set, การควบคุม CPA ด้วย Bid Cap/Cost Cap, การป้องกัน Starvation ด้วย Minimum Spend Threshold, ไปจนถึงการใช้ Automated Rules ลดงานที่ต้องเฝ้าจอ
