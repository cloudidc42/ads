## Step 601: "แคมเปญไม่วิ่ง" คืออะไร — อาการที่สังเกตได้ก่อนเริ่มวิเคราะห์สาเหตุ

### นิยามที่ต้องแยกให้ชัด

"แคมเปญไม่วิ่ง" มีหลายระดับที่มีสาเหตุต่างกันมาก การแยกระดับให้ถูกก่อนคือจุดเริ่มต้นของการ Troubleshoot ที่มีประสิทธิภาพ:

| ระดับ | อาการ | ความเร่งด่วน |
|---|---|---|
| ระดับ 1: ไม่ Active เลย | สถานะ Ad Set/Ad เป็น "Not Delivering" หรือ "Learning Limited" | สูง — ต้องแก้ทันที เพราะไม่มีการใช้งบเลย |
| ระดับ 2: Active แต่ Spend เป็น 0 หรือต่ำมาก | สถานะ Active แต่ผ่านมาหลายชั่วโมง/วันแล้ว Spend ยังไม่ขยับ | สูง |
| ระดับ 3: Spend ปกติแต่ Impression ต่ำผิดปกติ | ใช้เงินได้แต่ Reach คนน้อยมากเทียบ Budget | กลาง |
| ระดับ 4: Delivery ปกติแต่ผลลัพธ์ (Conversion) เป็น 0 | Spend/Impression ปกติ แต่ไม่มี Conversion เลย | กลาง-สูง ขึ้นกับ Budget ที่เสียไป |

### สิ่งแรกที่ต้องเช็คเสมอก่อนวิเคราะห์เชิงลึก

ก่อนไปดูสาเหตุซับซ้อน ให้เช็ค 3 อย่างนี้ก่อนเสมอ เพราะเป็นสาเหตุพื้นฐานที่สุดที่มักถูกมองข้าม:

1. **สถานะ Toggle เปิด/ปิด** — Campaign, Ad Set, และ Ad ทุกระดับต้องเป็น "Active" ทั้ง 3 ชั้น ถ้าชั้นใดชั้นหนึ่งถูกปิดไว้ (เช่น Ad Set Active แต่ Campaign ถูกปิดไว้) จะไม่วิ่งเลยแม้ระดับล่างจะเปิดอยู่
2. **Schedule/Date Range** — ตรวจว่า Start Date ยังไม่ถึง หรือ End Date ผ่านไปแล้วหรือไม่ และตรวจ Ad Scheduling (Dayparting) ว่าตั้งเวลาไว้ถูกต้องหรือไม่ (บางครั้งตั้งเวลาผิด Timezone ทำให้คิดว่าไม่วิ่งทั้งที่จริงมันวิ่งแค่ช่วงตี 3)
3. **Ad Account ถูก Restrict หรือ Payment ผ่านหรือไม่** — เข้า Billing > Payment Settings เช็คว่ามี Failed Payment หรือ Account มี Warning ใด ๆ

### อ่าน Delivery Status ให้เป็น

Meta แสดงสถานะ Delivery ที่ Ad Set Level ซึ่งบอกเบาะแสสำคัญ:

| สถานะที่แสดง | ความหมาย |
|---|---|
| Active | กำลังวิ่งปกติ (แต่ไม่ได้แปลว่าไม่มีปัญหาเสมอไป ต้องดู Spend/Impression ควบคู่) |
| Learning | อยู่ในช่วงเก็บข้อมูล Optimization ยังไม่นิ่ง |
| Learning Limited | ระบบเรียนรู้ไม่พอ มักเกิดจาก Budget ต่ำ/Audience แคบเกินกว่าจะได้ Conversion เพียงพอในสัปดาห์ |
| Not Delivering | ไม่ได้แสดงผลเลย ต้องไปดูรายละเอียดว่าติด Policy, Bid ต่ำ, หรือแข่งกับ Ad Set อื่นในบัญชี |
| In Review | โฆษณากำลังถูกตรวจสอบ Policy ยังไม่ได้แสดงผล |
| Rejected/Disapproved | โฆษณาถูกปฏิเสธ ต้องแก้ไขหรือ Appeal |
| Ad Account/Campaign Off | ถูกปิดในระดับบนสุด |

### ข้อผิดพลาดที่พบบ่อย

**รีบสรุปว่า "Facebook มีปัญหา" ก่อนเช็คพื้นฐาน** — ในความเป็นจริงกว่า 60–70% ของเคส "ไม่วิ่ง" มาจากสาเหตุพื้นฐานง่าย ๆ อย่าง Toggle ปิด, Schedule ผิด, หรือ Payment มีปัญหา ไม่ใช่ปัญหาซับซ้อนของระบบ

**ไม่แยกระดับความรุนแรงก่อนแก้** — พยายามแก้ทุกอย่างพร้อมกันโดยไม่รู้ว่าปัญหาอยู่ระดับไหน ทำให้เสียเวลาไปกับการแก้จุดที่ไม่ใช่ต้นเหตุจริง

## Step 602: สาเหตุการไม่ Deliver กลุ่มที่ 1 — Bid ต่ำเกินไป, Budget ต่ำเกินไป

### ปัญหา Bid ต่ำเกินไปเทียบกับ Auction

เมื่อใช้ Bid Strategy แบบ Cost Cap หรือ Bid Cap (เรียนใน Part 059) แล้วตั้งเพดานต่ำเกินกว่าที่ตลาด ณ ขณะนั้นจะแข่งขันได้ Ad Set ของคุณจะแพ้ Auction ตลอดเวลาและไม่ได้แสดงผลเลย หรือแสดงผลน้อยมากเฉพาะช่วงที่การแข่งขันต่ำ (เช่น ตอนดึก)

**วิธีตรวจสอบ:** ดู Column "Cost per Result" ของ Ad Set ที่เคยวิ่งได้ในช่วงก่อนหน้า หรือของคู่แข่งในอุตสาหกรรมเดียวกัน (จาก Benchมาr์คภายในทีมหรือประสบการณ์) เทียบกับ Cost Cap ที่ตั้งไว้ ถ้า Cost Cap ตั้งไว้ต่ำกว่าค่าเฉลี่ยตลาดมาก (เช่น ตลาดจริงอยู่ที่ 150 บาทต่อ Result แต่ตั้ง Cost Cap ไว้ 60 บาท) นี่คือสาเหตุที่ชัดเจน

**วิธีแก้:** ปรับ Cost Cap ขึ้นแบบค่อยเป็นค่อยไป (เพิ่ม 20–30% ต่อครั้ง) หรือเปลี่ยนกลับไปใช้ Lowest Cost ชั่วคราวเพื่อเก็บข้อมูล Baseline ราคาตลาดจริงก่อน แล้วค่อยกลับมาใช้ Cost Cap ด้วยตัวเลขที่สมเหตุสมผลกว่า

### ปัญหา Budget ต่ำเกินไปเทียบกับ Optimization Event

Meta ต้องการเห็นผลลัพธ์ (Conversion) อย่างน้อยประมาณ 50 ครั้งต่อสัปดาห์ต่อ Ad Set เพื่อให้ Algorithm เรียนรู้ได้อย่างมีประสิทธิภาพ (ตัวเลขนี้เป็นแนวทางที่ Meta แนะนำ ไม่ใช่กฎตายตัว) ถ้า Budget ต่ำเกินกว่าที่จะสร้าง Conversion ได้ถึงระดับนี้ Ad Set จะอยู่ในสถานะ "Learning Limited" ต่อเนื่อง และมักได้ Impression/Delivery ต่ำผิดปกติเพราะระบบไม่มั่นใจว่าจะหาคนที่ Convert ได้แม่นยำแค่ไหน

**วิธีตรวจสอบ:** คำนวณ Budget ÷ Cost per Result เฉลี่ยของอุตสาหกรรม/ประสบการณ์ที่ผ่านมา ถ้าตัวเลขที่ได้ (จำนวน Conversion ที่คาดว่าจะได้ต่อสัปดาห์) ต่ำกว่า 15–20 ครั้ง Budget อาจต่ำเกินไปสำหรับ Optimization Event นั้น

**วิธีแก้:** เพิ่ม Budget ให้เพียงพอ หรือเปลี่ยน Optimization Event ไปที่ Event ที่เกิดบ่อยกว่า (เช่น จาก Purchase ไปเป็น Add to Cart ชั่วคราวเพื่อให้ระบบเรียนรู้ได้ก่อน แล้วค่อยขยับกลับไป Purchase เมื่อ Budget/Volume เพียงพอ)

### ตารางสรุปสาเหตุกลุ่ม Bid/Budget

| สาเหตุ | อาการที่สังเกต | วิธีแก้ |
|---|---|---|
| Bid/Cost Cap ต่ำเกินไป | Impression ต่ำมาก, Delivery กระจุกตัวเฉพาะช่วงดึก | เพิ่ม Cap ทีละ 20-30% หรือกลับไป Lowest Cost ชั่วคราว |
| Budget ต่ำเทียบ Optimization Event | Learning Limited ต่อเนื่อง, Conversion Volume ต่ำกว่า 15-20/สัปดาห์ | เพิ่ม Budget หรือเปลี่ยน Event ให้เกิดบ่อยขึ้นชั่วคราว |
| Budget ต่ำเทียบขนาด Audience | Impression กระจุกตัว ไม่กระจายทั้งวัน | เพิ่ม Budget หรือลดขนาด Audience ให้สัมพันธ์กัน |

### ข้อผิดพลาดที่พบบ่อย

**เพิ่ม Budget ทันทีแบบก้าวกระโดด (มากกว่า 50% ในครั้งเดียว)** — ทำให้ Learning Phase รีเซ็ตและปัญหาแย่ลงกว่าเดิมช่วงแรก ควรเพิ่มแบบค่อยเป็นค่อยไปตามหลักการใน Part 059

**ตั้ง Cost Cap จากความรู้สึก ไม่มีข้อมูลอ้างอิง** — ตั้งเพดานต่ำเพราะ "อยากได้ CPA ถูก" โดยไม่เช็คราคาตลาดจริงก่อน

## Step 603: สาเหตุการไม่ Deliver กลุ่มที่ 2 — Audience แคบเกินไป, Audience Overlap

### ปัญหา Audience แคบเกินไป

เมื่อ Audience Size เล็กเกินไปเทียบกับ Budget ที่ตั้งไว้ ระบบจะหาคนแสดงผลได้ยาก เพราะ Pool ของคนที่ตรงเงื่อนไขมีจำกัด โดยเฉพาะเมื่อซ้อนเงื่อนไข Interest/Demographic หลายชั้นจนเหลือ Audience Size ต่ำกว่า 100,000–200,000 คน (ตัวเลขอ้างอิงคร่าว ๆ ขึ้นกับประเทศ/ตลาด)

**วิธีตรวจสอบ:** ดู Audience Size ที่แสดงในหน้า Ad Set Setup (ตัวเลขประมาณการ) เทียบกับ Budget ต่อวัน ถ้า Budget สูงเทียบกับ Audience Size ที่มี (เช่น Audience 50,000 คน แต่ Budget 3,000 บาท/วัน) ระบบจะเผา Audience หมดเร็วและ Delivery จะแย่ลงเรื่อย ๆ

**วิธีแก้:** ขยาย Audience โดยลดจำนวนเงื่อนไขที่ซ้อนกัน, ใช้ Lookalike ขนาดใหญ่ขึ้น (2-5% แทน 1%), หรือรวม Interest หลายกลุ่มเข้าด้วยกันแทนการซ้อนแบบ "Must Match All"

### ปัญหา Audience Overlap ระหว่าง Ad Set ในบัญชีเดียวกัน

Audience Overlap เกิดเมื่อหลาย Ad Set ในบัญชีเดียวกัน (หรือแม้แต่ Campaign เดียวกัน) เจาะกลุ่มเป้าหมายที่ทับซ้อนกันมาก ทำให้ Ad Set เหล่านี้แข่ง Auction กันเอง (Self-competition) ผลคือ Ad Set ที่มี Priority ต่ำกว่าในสายตาระบบจะแพ้และไม่ได้แสดงผลเลย ทั้งที่ Setting ดูปกติทุกอย่าง

**วิธีตรวจสอบ:** ใช้ Meta's Audience Overlap Tool (ใน Audience Manager เลือก Custom Audience ที่สร้างจาก Ad Set ที่สงสัยว่าทับซ้อน แล้วเทียบ % Overlap) ถ้า Overlap เกิน 20–30% ระหว่าง Ad Set ที่ Budget ใกล้เคียงกัน นี่คือสาเหตุที่เป็นไปได้สูง

**วิธีแก้:** รวม Ad Set ที่ Overlap สูงเข้าด้วยกันเป็น Ad Set เดียว (ให้ Algorithm เลือกเองว่าจะแสดงผลให้ใคร), ใช้ Exclusion เพื่อแยกกลุ่มไม่ให้ทับซ้อน (เช่น Ad Set A ตัดคนที่เคยเห็น Ad Set B ออก), หรือลดจำนวน Ad Set ที่เปิดพร้อมกันในกลุ่มเป้าหมายเดียวกัน

### ตารางสรุปสาเหตุกลุ่ม Audience

| สาเหตุ | อาการที่สังเกต | วิธีแก้ |
|---|---|---|
| Audience แคบเกินไป | Impression ต่ำ, Frequency พุ่งเร็วผิดปกติตั้งแต่วันแรก | ขยาย Audience Size, ลดเงื่อนไขที่ซ้อนกัน |
| Audience Overlap ระหว่าง Ad Set | Ad Set บาง Ad Set ไม่วิ่งเลยทั้งที่ Setting ปกติ | รวม Ad Set, ใช้ Exclusion, ลดจำนวน Ad Set ที่ทับซ้อน |
| Budget สูงเทียบ Audience Size | Delivery ดีตอนแรกแล้วแย่ลงเร็ว | เพิ่มขนาด Audience หรือลด Budget ให้สมดุล |

### ข้อผิดพลาดที่พบบ่อย

**เปิด Ad Set หลายตัวเจาะ Audience คล้ายกันเพื่อ "เผื่อ" ว่าตัวใดตัวหนึ่งจะดี** — วิธีนี้สร้าง Overlap โดยไม่ตั้งใจและทำให้ Ad Set บางตัวไม่มีโอกาสได้แสดงผลเลย ควรใช้ CBO ให้ระบบเลือกจัดสรร Budget เองแทนการเปิดหลาย Ad Set แข่งกันด้วยมือ

**ไม่เคยตรวจ Audience Overlap Tool เลย** — ปล่อยให้ Ad Set ใหม่ ๆ ทับซ้อนกับของเดิมสะสมมากขึ้นเรื่อย ๆ โดยไม่รู้ตัว

## Step 604: สาเหตุการไม่ Deliver กลุ่มที่ 3 — โฆษณาถูก Reject/Limited, ปัญหาการชำระเงิน

### โฆษณาถูก Reject/Disapproved

เมื่อโฆษณาถูกปฏิเสธ จะไม่แสดงผลเลยแม้ Ad Set/Campaign จะ Active อยู่ก็ตาม สาเหตุที่พบบ่อย (รายละเอียดเชิงลึกเรียนแล้วใน Part 020):
- ใช้คำที่ละเมิด Personal Attributes Policy (พูดถึงผู้อ่านโดยตรงเกี่ยวกับสภาพร่างกาย/การเงิน/สุขภาพ)
- ภาพ/วิดีโอมีข้อความเกิน 20% ของพื้นที่ภาพ (สำหรับบางประเภทโฆษณา แม้ Meta ผ่อนคลายกฎนี้ไปมากแล้วในปัจจุบันแต่ยังส่งผลต่อ Delivery ในบางกรณี)
- Landing Page มีเนื้อหาที่ขัดนโยบาย แม้ตัวโฆษณาเองจะดูปกติ
- ใช้ Before/After ที่ Overclaim ผลลัพธ์เกินจริง

**วิธีตรวจสอบ:** ไปที่ Ad Level เปิดดูสถานะ ถ้าเป็น "Rejected" จะมีปุ่ม "See Details" หรือ "Request Review" ที่บอกเหตุผลคร่าว ๆ ว่าละเมิดนโยบายหมวดไหน

**วิธีแก้:** แก้ไขเนื้อหาตามเหตุผลที่ระบุ แล้วส่ง Appeal ผ่านปุ่มที่ระบบให้มา (ระยะเวลาตรวจสอบปกติ 24–48 ชั่วโมง) หลีกเลี่ยงการสร้างโฆษณาใหม่ทับซ้ำ ๆ โดยไม่แก้ไขสาเหตุจริง เพราะจะสะสมเป็นความเสี่ยงต่อ Ad Account Quality โดยรวม

### สถานะ "In Review" ค้างนานผิดปกติ

โฆษณาปกติจะผ่านการตรวจสอบภายในไม่กี่นาทีถึงไม่กี่ชั่วโมง ถ้าค้างอยู่ที่ "In Review" นานกว่า 24 ชั่วโมง มักเกิดจากระบบตรวจสอบมีปริมาณงานมาก หรือโฆษณาเข้าเงื่อนไขที่ต้องตรวจสอบเพิ่มเติมด้วยคน (Manual Review) โดยเฉพาะหมวดที่มีความเสี่ยงสูง (สุขภาพ, การเงิน, ความงาม)

**วิธีแก้:** รอให้ครบ 24–48 ชั่วโมงก่อน ถ้ายังไม่ผ่านให้ติดต่อ Meta Support ผ่าน Business Help Center

### ปัญหาการชำระเงิน (Payment Issue)

Failed Payment เป็นสาเหตุที่ถูกมองข้ามบ่อยที่สุด เพราะ Ads Manager บางครั้งไม่แจ้งเตือนชัดเจนพอ อาการคือ Ad Set สถานะ Active แต่ Spend ไม่ขยับเลย

**วิธีตรวจสอบ:** ไปที่ Billing > Payment Settings เช็คว่ามี "Payment Failed" หรือ Amount Due ค้างอยู่หรือไม่ เช็คว่าบัตรเครดิต/เดบิตยังไม่หมดอายุ วงเงินคงเหลือพอหรือไม่ (สำหรับบัตรเดบิตที่มีเงินไม่พอ), หรือธนาคารบล็อกการทำรายการต่างประเทศ (Facebook เก็บเงินในสกุล USD บางกรณี ทำให้ธนาคารเข้าใจผิดว่าเป็นรายการผิดปกติแล้วบล็อก)

**วิธีแก้:** อัปเดต Payment Method ให้เป็นปัจจุบัน, เพิ่ม Payment Method สำรอง (บัตรที่ 2) ไว้เสมอเพื่อไม่ให้เกิดปัญหานี้ซ้ำ, ติดต่อธนาคารให้ปลดบล็อกรายการต่างประเทศล่วงหน้าก่อนยิงแอด

### ตารางสรุปสาเหตุกลุ่ม Policy/Payment

| สาเหตุ | อาการที่สังเกต | วิธีแก้ |
|---|---|---|
| Ad Rejected | สถานะ Rejected ชัดเจน | แก้เนื้อหาตามเหตุผล + Appeal |
| In Review ค้างนาน | สถานะ In Review เกิน 24 ชม. | รอ 24-48 ชม. แล้ว Contact Support |
| Payment Failed | Active แต่ Spend ไม่ขยับ | อัปเดต/เพิ่ม Payment Method สำรอง |
| Ad Account Restricted | ทุก Campaign ไม่วิ่งพร้อมกัน | ตรวจ Account Quality + Appeal ตาม Part 020 |

### ข้อผิดพลาดที่พบบ่อย

**สร้างโฆษณาใหม่ทับซ้ำเมื่อถูก Reject โดยไม่แก้สาเหตุ** — ยิ่งทำให้ Ad Account Quality แย่ลง เพิ่มความเสี่ยงถูก Restrict ทั้งบัญชี

**ไม่เตรียม Payment Method สำรองไว้ล่วงหน้า** — ทำให้เมื่อบัตรหลักมีปัญหา แคมเปญหยุดวิ่งกลางอากาศโดยไม่มีทางแก้ทันที

## Step 605: Troubleshooting Flowchart แบบสมบูรณ์สำหรับปัญหา "ไม่วิ่ง"

### หลักการของ Flowchart: ไล่จากสาเหตุที่พบบ่อย/แก้ง่ายที่สุดไปหายากที่สุด

การไล่ตรวจแบบสุ่มเสียเวลามาก Flowchart นี้เรียงลำดับให้ไล่ตรวจจากสิ่งที่ **มีโอกาสเป็นสาเหตุมากที่สุดและแก้ง่ายที่สุดก่อน** ไปจนถึงสิ่งที่ซับซ้อนกว่า

### ขั้นที่ 1: เช็คโครงสร้างพื้นฐาน (ใช้เวลา 2 นาที)

- Campaign, Ad Set, Ad ทั้ง 3 ชั้น Active ทั้งหมดหรือไม่? → ถ้าไม่ Active ให้เปิด แล้วหยุด Flowchart ตรงนี้
- Schedule/Date Range ถูกต้องหรือไม่? → ถ้าผิดให้แก้ แล้วหยุด Flowchart ตรงนี้
- ถ้าผ่านทั้ง 2 ข้อ → ไปขั้นที่ 2

### ขั้นที่ 2: เช็ค Payment และ Account Status (ใช้เวลา 3 นาที)

- Billing มี Failed Payment หรือไม่? → ถ้ามีให้แก้ไข Payment Method แล้วหยุด Flowchart ตรงนี้
- Ad Account มี Restriction/Warning หรือไม่? → ถ้ามีให้ไปตามกระบวนการ Appeal (Part 020) แล้วหยุด Flowchart ตรงนี้
- ถ้าผ่านทั้ง 2 ข้อ → ไปขั้นที่ 3

### ขั้นที่ 3: เช็คสถานะ Ad ระดับ Creative (ใช้เวลา 3 นาที)

- Ad สถานะ Rejected หรือไม่? → ถ้าใช่ ไปแก้เนื้อหาตาม Step 604 แล้วหยุด Flowchart ตรงนี้
- Ad สถานะ In Review ค้างเกิน 24 ชม.หรือไม่? → ถ้าใช่ รอเพิ่มหรือ Contact Support
- ถ้าผ่านทั้ง 2 ข้อ → ไปขั้นที่ 4

### ขั้นที่ 4: เช็ค Bid/Budget (ใช้เวลา 5 นาที)

- ใช้ Cost Cap/Bid Cap หรือไม่ ถ้าใช่ตั้งไว้ต่ำกว่าตลาดหรือไม่ (ดู Step 602)? → ถ้าใช่ ปรับเพิ่มทีละ 20-30%
- Budget สัมพันธ์กับ Optimization Event Volume ที่ต้องการหรือไม่ (Step 602)? → ถ้าไม่ ปรับ Budget หรือเปลี่ยน Event
- ถ้าผ่านทั้ง 2 ข้อ → ไปขั้นที่ 5

### ขั้นที่ 5: เช็ค Audience (ใช้เวลา 5-10 นาที)

- Audience Size เล็กเกินไปเทียบ Budget หรือไม่ (Step 603)? → ถ้าใช่ ขยาย Audience
- มี Audience Overlap กับ Ad Set อื่นในบัญชีหรือไม่ (Step 603)? → ถ้ามี รวม/แยก Ad Set ตามคำแนะนำ
- ถ้าผ่านทั้ง 2 ข้อ → ไปขั้นที่ 6

### ขั้นที่ 6: ปัญหาระดับที่ซับซ้อนกว่า (ต้องใช้เวลาสืบสวนมากขึ้น)

- ตรวจ Ad Relevance Diagnostics ว่ามี Ranking แย่ผิดปกติจากตอนสร้างครั้งแรกหรือไม่
- ตรวจว่า Landing Page ล่ม/โหลดช้าจนกระทบ Quality Score หรือไม่
- ถ้าตรวจครบทุกขั้นแล้วยังไม่พบสาเหตุ → Escalate ไปที่ Meta Support ตาม Step 609 พร้อมเอกสารสรุปทุกขั้นที่ตรวจมาแล้ว

### ตารางสรุป Flowchart แบบย่อ (ใช้พิมพ์แขวนหน้าจอได้)

| ขั้น | คำถาม | ถ้า "มีปัญหา" ทำอะไร |
|---|---|---|
| 1 | Active ครบ 3 ชั้น + Schedule ถูกไหม | เปิด/แก้ Schedule |
| 2 | Payment/Account ปกติไหม | แก้ Payment, Appeal Restriction |
| 3 | Ad Rejected/In Review นานไหม | แก้เนื้อหา, Appeal, รอ/Contact Support |
| 4 | Bid/Budget เหมาะสมไหม | ปรับ Cap/Budget ทีละน้อย |
| 5 | Audience เล็ก/Overlap ไหม | ขยาย/รวม/แยก Audience |
| 6 | ยังไม่พบสาเหตุ | Escalate Meta Support |

### ข้อผิดพลาดที่พบบ่อย

**ข้ามขั้นตอนไปแก้จุดที่ซับซ้อนก่อน** — ไปยุ่งกับ Audience Overlap ก่อนเช็คว่า Payment มีปัญหาหรือไม่ ทำให้เสียเวลาโดยไม่จำเป็น

**ไม่บันทึกว่าตรวจอะไรไปแล้วบ้าง** — ทำให้เมื่อต้อง Escalate ไปที่ Meta Support ไม่มีข้อมูลสรุปให้ ทำให้กระบวนการ Support ช้าลงไปอีก

## Step 606: สาเหตุ "CPA สูง" กลุ่มที่ 1 — Optimization Event ผิด, Creative อ่อน, Offer อ่อน

### ปัญหา Optimization Event ผิด

การเลือก Optimization Event ที่ไม่ตรงกับเป้าหมายจริงเป็นสาเหตุที่พบบ่อยและถูกมองข้ามบ่อยที่สุด เช่น ตั้ง Ad Set ให้ Optimize เพื่อ Landing Page View ทั้งที่เป้าหมายจริงคือ Purchase — ระบบจะหาคนที่มีโอกาส "เปิดหน้าเว็บ" สูง ไม่ใช่คนที่มีโอกาส "ซื้อ" สูง ทำให้ได้ Traffic จำนวนมากแต่ Conversion Rate ต่ำ CPA จึงสูงเมื่อคำนวณจาก Purchase จริง

**วิธีตรวจสอบ:** เปิด Ad Set Setting ดู Optimization Goal ที่เลือกไว้ เทียบกับ Metric ที่ใช้วัดความสำเร็จจริงของธุรกิจ ถ้าไม่ตรงกัน นี่คือสาเหตุที่ชัดเจนมาก

**วิธีแก้:** เปลี่ยน Optimization Event ให้ตรงกับเป้าหมายจริง แต่ถ้า Event เป้าหมาย (เช่น Purchase) มี Volume ต่ำเกินไปที่จะ Optimize ได้ตรง ให้ไต่ระดับผ่าน Event ตัวกลางก่อน (Add to Cart → Purchase) ตามหลักการใน Part 013 และ 015

### ปัญหา Creative อ่อน (ไม่ใช่ Fatigue แต่อ่อนตั้งแต่ต้น)

ต้องแยกจาก Ad Fatigue ที่เรียนใน Part 060 — Creative อ่อนหมายถึงครีเอทีฟที่ตั้งแต่วันแรกก็ทำ CTR/Conversion Rate ต่ำกว่ามาตรฐานอยู่แล้ว ไม่ใช่เคยดีแล้วค่อยแย่ลง

**วิธีตรวจสอบ:** เทียบ CTR ตั้งแต่วันแรกกับ Benchmark ของ Ad Set อื่นในบัญชีเดียวกันหรืออุตสาหกรรมเดียวกัน ถ้าต่ำกว่ามาตรฐานตั้งแต่เริ่มต้น (ไม่ใช่ค่อย ๆ ลดลง) ปัญหาอยู่ที่คุณภาพ Creative ตั้งแต่แรก ไม่ใช่ Fatigue

**วิธีแก้:** กลับไปที่หลักการ Creative ที่หยุดสกอร์ (Part 036) และ Copywriting (Part 037-038) ทบทวน Hook, Value Proposition, และ Call-to-Action ใหม่ทั้งหมด

### ปัญหา Offer อ่อน (สินค้า/ข้อเสนอไม่น่าดึงดูดพอ)

บางครั้งปัญหาไม่ได้อยู่ที่การยิงแอดเลย แต่อยู่ที่ Offer เองไม่น่าสนใจพอเทียบกับคู่แข่งหรือเทียบกับสิ่งที่ตลาดคาดหวัง ปัญหานี้จะปรากฏเป็น CPA สูงไม่ว่าจะเปลี่ยน Creative/Audience กี่รอบก็ตาม เพราะรากปัญหาไม่ใช่การสื่อสาร แต่เป็นตัวสินค้า/ข้อเสนอเอง

**วิธีตรวจสอบ:** ดู Conversion Rate ของ Landing Page (ไม่ใช่แค่ CTR ของโฆษณา) เทียบกับ Benchmark อุตสาหกรรม ถ้า CTR ดี (คนสนใจคลิก) แต่ Conversion Rate ต่ำมาก (คลิกแล้วไม่ซื้อ) ทั้งที่ Landing Page ไม่มีปัญหาเชิงเทคนิค (ตาม Part 054) ปัญหาน่าจะอยู่ที่ Offer เอง

**วิธีแก้:** ทบทวน Value Proposition (Part 003, 005), เทียบราคา/เงื่อนไขกับคู่แข่งผ่าน Ad Library, พิจารณาปรับ Offer เช่น เพิ่ม Guarantee, ปรับ Bundle, หรือปรับราคา

### ตารางสรุปสาเหตุกลุ่มที่ 1

| สาเหตุ | สัญญาณเฉพาะ | วิธีตรวจ | วิธีแก้ |
|---|---|---|---|
| Optimization Event ผิด | Traffic สูง Conversion ต่ำ | เช็ค Optimization Goal Setting | เปลี่ยน Event ให้ตรงเป้าหมายจริง |
| Creative อ่อนตั้งแต่ต้น | CTR ต่ำตั้งแต่วันแรก ไม่ใช่ค่อยลด | เทียบ Benchmark วันแรก | ทบทวน Hook/Copy ใหม่ |
| Offer อ่อน | CTR ดี แต่ Conversion Rate ต่ำ ทุก Creative | เทียบ Conversion Rate กับ Benchmark | ปรับ Value Proposition/ราคา/Guarantee |

### ข้อผิดพลาดที่พบบ่อย

**โทษ Creative ทั้งที่ปัญหาจริงคือ Optimization Event** — เปลี่ยนภาพ/วิดีโอหลายรอบแต่ CPA ไม่ลง เพราะสาเหตุจริงอยู่ที่ Setting ไม่ใช่ Creative

**ไม่แยกระหว่าง CTR (ความสนใจ) กับ Conversion Rate (การตัดสินใจซื้อ)** — สอง Metric นี้บอกปัญหาคนละจุด ต้องดูควบคู่กันเพื่อระบุว่าปัญหาอยู่ที่ Creative หรือ Offer/Landing Page

## Step 607: สาเหตุ "CPA สูง" กลุ่มที่ 2 — Audience ผิด, Landing Page มีปัญหา, Seasonality/Competition

### ปัญหา Audience ผิด (ไม่ใช่แคบ แต่ผิดกลุ่ม)

ต่างจาก Step 603 ที่พูดถึง Audience แคบจนไม่ Deliver ปัญหานี้คือ Audience มีขนาดพอ Deliver ได้ปกติ แต่เป็นกลุ่มคนที่ไม่ตรงกับผู้ที่มีโอกาสซื้อจริง เช่น Interest ที่เลือกกว้างเกินไปจนได้คนที่ไม่ใช่ลูกค้าเป้าหมาย หรือ Lookalike ที่สร้างจาก Source Audience คุณภาพต่ำ (เช่น สร้างจาก "คนที่กด Like เพจ" ซึ่งมีคุณภาพต่ำกว่า "คนที่ซื้อแล้ว")

**วิธีตรวจสอบ:** ดู Demographic Breakdown ของ Conversion จริง (Age, Gender, Placement) เทียบกับ Persona ที่ตั้งใจเจาะ ถ้าคนที่ Convert จริงกระจุกตัวในกลุ่มที่ต่างจาก Audience Setting มาก อาจแปลว่า Audience ที่ตั้งไว้กว้าง/ผิดกลุ่มเกินไปและปล่อยให้ Algorithm หาคนที่ใช่เองมากกว่าที่ Targeting ช่วย

**วิธีแก้:** ปรับ Source Audience ของ Lookalike ให้มาจากกลุ่มคุณภาพสูงกว่า (Purchaser ไม่ใช่แค่ Website Visitor), ทดสอบ Advantage+ Audience ให้ระบบ AI ช่วยหา, หรือเก็บ Interest ที่แคบลงแต่ตรง Persona มากขึ้น

### ปัญหา Landing Page (แม้ผ่าน Basic Checklist แล้ว)

Part 054 สอนพื้นฐาน Landing Page ที่ต้องมี แต่บางครั้งปัญหา CPA สูงเกิดจากรายละเอียดที่ไม่ใช่ "พื้นฐานที่ขาด" แต่เป็น Message Match ที่ไม่สอดคล้องระหว่างโฆษณากับหน้า Landing Page เช่น โฆษณาพูดถึงโปรโมชัน A แต่หน้า Landing Page ไม่มีโปรโมชันนั้นแสดงชัดเจน ทำให้คนที่คลิกเข้ามาด้วยความคาดหวังหนึ่งแล้วเจอสิ่งที่ไม่ตรง (Bait-and-switch Effect แม้ไม่ได้ตั้งใจ) จนออกจากหน้าทันที

**วิธีตรวจสอบ:** เปิดโฆษณาและ Landing Page เทียบข้าง ๆ กันเหมือนเป็นลูกค้าจริง ดูว่า Message, ราคา, Offer ตรงกันทุกจุดหรือไม่ เช็ค Bounce Rate ผ่าน Analytics ว่าสูงผิดปกติเทียบ Benchmark หรือไม่ (Bounce Rate ที่สูงกว่า 70-80% สำหรับ Landing Page ที่ออกแบบมาเฉพาะสำหรับแอด ถือว่าน่าสงสัย)

**วิธีแก้:** แก้ Message Match ให้ตรงกันระหว่างโฆษณาและหน้า Landing Page ทุกจุด ตรวจสอบ Page Speed อีกครั้งเฉพาะบน Mobile 4G (ไม่ใช่ WiFi Office ที่เร็วผิดปกติ)

### ปัญหา Seasonality/Competition (ปัจจัยตลาดที่ควบคุมไม่ได้)

CPA สูงบางครั้งไม่ได้เกิดจากอะไรที่คุณทำผิด แต่เกิดจากการแข่งขันในตลาดสูงขึ้น (คู่แข่งเพิ่ม Budget ในช่วงเดียวกัน ดันราคา Auction ขึ้นทั้งตลาด) หรือ Demand ตามฤดูกาลลดลง (รายละเอียดเต็มใน Part 062)

**วิธีตรวจสอบ:** เช็ค Facebook Ad Library ว่าคู่แข่งในหมวดเดียวกันเพิ่มจำนวนโฆษณา Active หรือไม่ เช็ค Google Trends ของ Keyword หลักของธุรกิจ เทียบ CPM ปัจจุบันกับ Baseline ของช่วงเวลาปีก่อนหน้า (ถ้ามีข้อมูล)

**วิธีแก้:** ถ้าเป็นปัจจัยตลาดที่ควบคุมไม่ได้จริง อาจต้องยอมรับ CPA ที่สูงขึ้นชั่วคราวและปรับ ROAS Target ให้สมเหตุสมผลกับสถานการณ์ หรือลด Budget ลงชั่วคราวจนกว่าการแข่งขันจะซาลง

### ตารางสรุปสาเหตุกลุ่มที่ 2

| สาเหตุ | สัญญาณเฉพาะ | วิธีแก้ |
|---|---|---|
| Audience ผิดกลุ่ม | Conversion กระจุกตัวต่างจาก Targeting ที่ตั้งไว้ | ปรับ Source Audience/Lookalike, ใช้ Advantage+ |
| Landing Page Message Mismatch | Bounce Rate สูงผิดปกติ | แก้ Message Match ให้ตรงโฆษณา |
| Seasonality/Competition | CPM ตลาดรวมสูงขึ้นพร้อมคู่แข่ง | ปรับ ROAS Target ชั่วคราว หรือลด Budget |

### ข้อผิดพลาดที่พบบ่อย

**พยายามแก้ปัจจัยที่ควบคุมไม่ได้ด้วยการเปลี่ยน Setting ในบัญชี** — เมื่อสาเหตุคือ Seasonality/Competition การไปเปลี่ยน Audience/Creative ซ้ำแล้วซ้ำอีกจะไม่ช่วย ควรยอมรับสถานการณ์และปรับ Target ให้สมจริง

**ไม่เคยเปิด Landing Page เทียบกับโฆษณาแบบเป็นลูกค้าจริง** — มองแค่ตัวเลขในระบบโดยไม่เคยไปดูหน้าจริงว่า Message ตรงกันหรือไม่

## Step 608: Isolating Variables — เปลี่ยนทีละตัวแปรอย่างเป็นระบบ

### หลักการพื้นฐาน: เปลี่ยนทีละอย่าง วัดผลก่อนเปลี่ยนต่อ

นี่คือหลักการที่สำคัญที่สุดในบทนี้ทั้งหมด เมื่อเจอปัญหา CPA สูงหรือไม่วิ่ง สิ่งที่มือใหม่ทำบ่อยที่สุดคือ "แก้ทุกอย่างพร้อมกัน" — เปลี่ยน Audience, Creative, Budget, Optimization Event ในครั้งเดียว ผลคือถ้า CPA ดีขึ้น จะไม่รู้ว่าอะไรคือตัวที่แก้ปัญหาได้จริง และถ้าเจอปัญหาแบบเดียวกันอีกในอนาคต จะต้องเดาใหม่ทั้งหมด

### กระบวนการ Isolating Variables ที่ใช้งานได้จริง

**ขั้นที่ 1: บันทึก Baseline ก่อนเปลี่ยนแปลงใด ๆ**

จดตัวเลขทุก Metric สำคัญ (CTR, CPM, CPC, Conversion Rate, CPA) ของสถานะปัจจุบันไว้เป็นจุดอ้างอิง

**ขั้นที่ 2: จัดลำดับความสำคัญของตัวแปรที่จะทดสอบ**

ใช้กรอบคิดแบบเดียวกับ Step 542 (CRO) — เริ่มจากตัวแปรที่มีผลกระทบสูงสุดและมีหลักฐานสนับสนุนแรงที่สุดจากการวิเคราะห์ Step 606-607 ก่อน ไม่ใช่ตัวแปรที่ทำง่ายที่สุด

**ขั้นที่ 3: เปลี่ยนตัวแปรเดียว รอผลลัพธ์อย่างน้อย 3-5 วัน (หรือจนพ้น Learning Phase)**

ระยะเวลารอควรสัมพันธ์กับ Volume ของ Conversion — ถ้า Ad Set มี Conversion น้อย ต้องรอนานขึ้นเพื่อให้มีข้อมูลพอสรุปผลได้อย่างมีนัยสำคัญ

**ขั้นที่ 4: บันทึกผลลัพธ์ เทียบกับ Baseline**

ถ้าดีขึ้นชัดเจน → เก็บการเปลี่ยนแปลงนี้ไว้ แล้วไปทดสอบตัวแปรถัดไป
ถ้าไม่เปลี่ยน/แย่ลง → ย้อนกลับไปตั้งค่าเดิม แล้วไปทดสอบตัวแปรถัดไปในรายการ

**ขั้นที่ 5: ทำซ้ำจนกว่าจะได้ผลลัพธ์ที่ยอมรับได้ หรือหมดสมมติฐานที่มี**

### ตัวอย่างการ Isolate Variable ในสถานการณ์จริง

สมมติแคมเปญมี CPA สูง 2 เท่าของ Target หลังวิเคราะห์ตาม Step 606-607 พบว่ามี 3 สมมติฐานที่เป็นไปได้: (1) Optimization Event ผิด (2) Creative อ่อน (3) Audience ผิดกลุ่ม

| รอบ | ตัวแปรที่เปลี่ยน | ระยะเวลาทดสอบ | ผลลัพธ์ | การตัดสินใจ |
|---|---|---|---|---|
| 1 | เปลี่ยน Optimization Event จาก Landing Page View เป็น Purchase | 5 วัน | CPA ลดลง 15% (ยังไม่พอ) | เก็บการเปลี่ยนนี้ไว้ ทดสอบตัวแปรถัดไป |
| 2 | เปลี่ยน Creative เป็นชุดใหม่ (Message เดิม) | 5 วัน | CPA ลดลงอีก 25% | เก็บไว้ ใกล้ Target แล้ว |
| 3 | ปรับ Source Audience ของ Lookalike เป็น Purchaser | 7 วัน | CPA ลดลงอีก 20% เข้า Target | หยุดที่นี่ ได้ผลลัพธ์ที่ต้องการ |

จากตัวอย่างนี้ จะเห็นว่าปัญหาจริงเป็น **การผสมกันของ 3 สาเหตุ** ไม่ใช่สาเหตุเดียว การ Isolate ทีละตัวทำให้รู้ว่าแต่ละตัวช่วยได้กี่ % และรู้ว่าควรทำอะไรก่อนถ้าเจอปัญหาแบบเดียวกันอีกในอนาคต (เริ่มจาก Optimization Event ก่อนเสมอ)

### ข้อยกเว้น: เมื่อสถานการณ์เร่งด่วนจนไม่มีเวลา Isolate ทีละตัว

ถ้าแคมเปญกำลังขาดทุนหนักและต้องหยุดความเสียหายทันที การรอ Isolate ทีละตัวอาจไม่ทันเวลา ในกรณีนี้ให้ลด Budget ลงก่อนเพื่อจำกัดความเสียหาย (ไม่ใช่ Pause เต็มที่จะเสีย Learning ทั้งหมด) แล้วค่อยกลับมา Isolate Variable อย่างเป็นระบบเมื่อสถานการณ์ไม่เร่งด่วนแล้ว

### ข้อผิดพลาดที่พบบ่อย

**เปลี่ยนหลายตัวแปรพร้อมกันเพราะรีบเห็นผล** — ได้ผลลัพธ์เร็วขึ้นจริง แต่ไม่ได้ Learning ที่นำไปใช้ต่อได้

**รอผลลัพธ์ไม่นานพอก่อนตัดสินใจ** — ดูผล 1 วันแล้วสรุปทันที ทั้งที่ Noise รายวันสูงมาก ทำให้ตัดสินใจผิดพลาดบ่อย

## Step 609: เมื่อไหร่ควร Kill เมื่อไหร่ควรทดสอบต่อ + Escalation Path (Meta Support)

### กรอบการตัดสินใจ Kill vs Continue Testing

การตัดสินใจนี้ต้องอิงจาก 3 ปัจจัย: **Volume ของข้อมูลที่มี, ระยะเวลาที่ทดสอบมาแล้ว, และ Budget ที่เหลือ/ความเสียหายสะสม**

| สถานการณ์ | คำแนะนำ |
|---|---|
| ทดสอบมาน้อยกว่า 3 วัน หรือ Conversion น้อยกว่า 10-15 ครั้ง | ยังทดสอบต่อ — ข้อมูลไม่พอสรุปอะไรได้เลย |
| ทดสอบมาครบตามที่วางแผน (5-7 วัน) แต่ CPA ยังสูงกว่า Target 50%+ ในทุกตัวแปรที่ลองแล้ว | พิจารณา Kill — สมมติฐานที่มีทั้งหมดหมดแล้วยังไม่ได้ผล |
| CPA สูงกว่า Target แต่ลดลงต่อเนื่องทุกรอบที่ Isolate Variable | ทดสอบต่อ — มีแนวโน้มบวก ยังมีสมมติฐานที่ยังไม่ลองครบ |
| ขาดทุนสะสมเกิน Threshold ที่ตั้งไว้ล่วงหน้า (เช่น 3x ของ Budget ทดสอบที่วางแผนไว้) | Kill ทันที ไม่ว่าจะมีสมมติฐานเหลือหรือไม่ — ป้องกันความเสียหายลุกลาม |

### กำหนด Kill Threshold ล่วงหน้าก่อนเริ่มทดสอบเสมอ

หลักการสำคัญที่ป้องกันการตัดสินใจด้วยอารมณ์: ก่อนเริ่ม Troubleshoot ทุกครั้ง ให้กำหนดไว้ล่วงหน้าว่า "จะยอมเสียเงินทดสอบสูงสุดกี่บาท/กี่วัน ก่อนที่จะ Kill โดยไม่มีข้อยกเว้น" เขียนตัวเลขนี้ไว้เป็นลายลักษณ์อักษรก่อนเริ่ม เพื่อไม่ให้ตัวเองหรือทีมงาน "เสียดาย" เงินที่ลงไปแล้ว (Sunk Cost Fallacy) จนทดสอบต่อไปเรื่อย ๆ โดยไม่มีเหตุผลรองรับ

### เมื่อไหร่ควร Escalate ไปที่ Meta Support

Meta Support ควรใช้เมื่อปัญหาชัดเจนว่าเป็นเรื่องของ **ระบบ/บัญชี** ไม่ใช่เรื่องของ Strategy/Creative/Offer ตัวอย่างสถานการณ์ที่ควร Escalate:
- Ad Account/Page ถูก Restrict โดยไม่มีเหตุผลชัดเจนหรือ Appeal ไม่ผ่านหลายรอบ
- Payment ผ่านแล้วแต่ระบบยังแสดง Failed Payment (Bug ของระบบ)
- โฆษณาถูก Reject ทั้งที่ตรวจสอบแล้วไม่ผิดนโยบายใดตามที่เข้าใจ (ต้อง Appeal ก่อน ถ้า Appeal ปฏิเสธซ้ำและมั่นใจว่าไม่ผิดจริง ค่อย Escalate)
- Pixel/CAPI มีปัญหาการส่งข้อมูลที่ตรวจสอบด้วยตัวเองแล้วไม่พบสาเหตุจากฝั่งเว็บไซต์

### เมื่อไหร่ "ไม่ใช่" ปัญหาของ Platform (ไม่ควร Escalate)

- CPA สูงเพราะ Offer ไม่น่าดึงดูดพอ — เป็นปัญหาธุรกิจ ไม่ใช่ Platform
- Frequency สูงเพราะ Audience เล็ก — เป็นปัญหาการตั้งค่าของผู้ยิงแอดเอง แก้ได้ด้วยตัวเอง
- Conversion Rate ต่ำเพราะ Landing Page ช้า — เป็นปัญหาฝั่งเว็บไซต์ของธุรกิจ

Meta Support ไม่สามารถช่วยแก้ปัญหาเชิง Strategy ได้ พวกเขาช่วยเฉพาะปัญหาเชิงเทคนิค/นโยบายของ Platform เท่านั้น การ Escalate ปัญหาที่ไม่เกี่ยวกับ Platform จะเสียเวลาทั้งสองฝ่ายโดยไม่ได้คำตอบที่เป็นประโยชน์

### วิธี Escalate อย่างมีประสิทธิภาพ

1. เข้า Meta Business Help Center > เลือกหมวดปัญหาที่ตรงที่สุด
2. เตรียมข้อมูลให้ครบก่อนติดต่อ: Ad Account ID, Campaign/Ad Set ID ที่มีปัญหา, สรุปสิ่งที่ตรวจสอบมาแล้ว (อ้างจาก Flowchart Step 605), Screenshot ของ Error/สถานะที่พบ
3. อธิบายปัญหาให้ชัดเจน กระชับ ไม่ใช่บรรยายอารมณ์ — บอกสิ่งที่คาดหวังให้เกิดขึ้นเทียบกับสิ่งที่เกิดขึ้นจริง
4. ถ้ามี Agency/Partner Support (สำหรับบัญชีที่ใช้งบสูงหรือผ่าน Agency) ให้ใช้ช่องทางนั้นเพราะมักได้การตอบกลับเร็วกว่าช่องทางทั่วไป

### ข้อผิดพลาดที่พบบ่อย

**ทดสอบต่อไปเรื่อย ๆ เพราะเสียดายเงินที่ลงไปแล้ว (Sunk Cost)** — ไม่มี Threshold ที่ชัดเจนล่วงหน้า ทำให้ขาดทุนสะสมมากกว่าที่ควร

**Escalate ปัญหาเชิง Strategy ไปที่ Meta Support** — เสียเวลารอคำตอบที่ไม่ช่วยแก้ปัญหาจริง ควรแก้ด้วยตัวเองตาม Framework ใน Step 606-608 ก่อน

### แม่แบบข้อความสำหรับ Escalate ไปที่ Meta Support

การเขียนข้อความที่มีโครงสร้างชัดเจนทำให้ได้รับการตอบกลับที่ตรงจุดเร็วขึ้นมาก แม่แบบที่แนะนำ:

```
หัวข้อ: [ปัญหาที่พบ] บน Ad Account ID: [หมายเลข]

รายละเอียดปัญหา: อธิบาย 1-2 บรรทัดว่าเกิดอะไรขึ้น
สิ่งที่คาดหวัง: บอกว่าปกติควรเป็นอย่างไร
สิ่งที่ตรวจสอบมาแล้ว: ระบุเป็น bullet ว่าตรวจอะไรไปแล้วบ้างตาม Flowchart
Ad Set ID / Ad ID ที่มีปัญหา: ระบุให้ชัดเจน
Screenshot: แนบภาพสถานะ/ข้อความ Error ที่พบ
```

การให้ข้อมูลครบตั้งแต่ข้อความแรกช่วยลดจำนวนรอบการถาม-ตอบกับทีม Support ได้มาก โดยเฉลี่ยอาจลดเวลาการแก้ปัญหาจาก 3-4 วันเหลือ 1-2 วัน

## Step 610: Case Study เต็มรูปแบบ + Workshop — Troubleshoot 3 สถานการณ์จำลอง

### Case Study: ร้านค้าออนไลน์เครื่องใช้ในบ้านที่ CPA พุ่ง 3 เท่าในสัปดาห์เดียว

ร้านค้าออนไลน์ขายเครื่องใช้ในบ้าน (เตาไฟฟ้า, หม้อทอดไม่ใช้น้ำมัน) ยิงแคมเปญ Conversion มาต่อเนื่อง 2 เดือนด้วย CPA เฉลี่ย 180 บาท ROAS 3.8 อยู่ ๆ สัปดาห์ที่ 9 CPA พุ่งเป็น 540 บาท (เกือบ 3 เท่า) โดยไม่มีการเปลี่ยนแปลงอะไรจากฝั่งทีมงานเลย

**ขั้นที่ 1 — เช็คโครงสร้างพื้นฐาน (Step 605 ขั้น 1-3):** ทุกอย่าง Active ปกติ, Payment ผ่านปกติ, ไม่มี Ad ถูก Reject — ตัดปัญหากลุ่มนี้ออก

**ขั้นที่ 2 — วิเคราะห์ CPA สูงตาม Step 606-607:**
- Optimization Event: ยังเป็น Purchase เหมือนเดิม ไม่เปลี่ยน — ตัดออก
- Creative: CTR ลดลงจาก 1.8% เป็น 1.1% (ลดลง ~39%) — น่าสงสัย
- Frequency: เพิ่มจาก 2.1 เป็น 4.6 ในสัปดาห์เดียว — สัญญาณ Fatigue ชัดเจน (เชื่อมกับ Part 060)
- Landing Page: เช็ค Message Match ปกติ ไม่มีอะไรเปลี่ยน — ตัดออก
- Seasonality/Competition: เช็ค Ad Library คู่แข่ง 3 รายในหมวดเดียวกัน พบว่าจำนวนโฆษณา Active เพิ่มขึ้นจาก 2-3 ตัวเป็น 8-12 ตัวต่อราย — สัญญาณว่าตลาดกำลังแข่งขันสูงขึ้น (ตรงกับช่วงเทศกาลลดราคาปลายปีที่ทุกรายเข้ามาแย่งพร้อมกัน)

**ขั้นที่ 3 — Isolate Variable (Step 608):**

| รอบ | ตัวแปรที่เปลี่ยน | ผลลัพธ์ |
|---|---|---|
| 1 | สลับ Creative ใหม่ (แก้ Fatigue) | CPA ลดจาก 540 เป็น 420 บาท (ดีขึ้นแต่ยังไม่ถึง Target) |
| 2 | ขยาย Audience (ลดผลกระทบจาก Frequency พุ่ง) | CPA ลดเป็น 340 บาท |
| 3 | ยอมรับว่าส่วนที่เหลือมาจาก Seasonality/Competition ปรับ ROAS Target ชั่วคราวจาก 3.8 เป็น 2.5 และคง Budget ระดับเดิม | CPA คงที่ 320-350 บาท ธุรกิจยังทำกำไรได้ที่ระดับนี้แม้ไม่เท่าเดิม |

**บทเรียน:** ปัญหาจริงเป็นการผสมกันของ Ad Fatigue (ที่สะสมมานานแต่ไม่มีใครสังเกต) และ Seasonal Competition ที่มาซ้อนกันในเวลาเดียวกัน ถ้าทีมงานรีบสรุปว่าเป็นแค่สาเหตุเดียว (เช่น คิดว่าเป็น Fatigue อย่างเดียว) จะพยายามแก้ต่อไปเรื่อย ๆ โดยไม่เข้าใจว่าทำไม CPA ไม่กลับไปที่ 180 บาทเหมือนเดิม การยอมรับปัจจัยตลาดที่ควบคุมไม่ได้ (ปรับ ROAS Target) เป็นส่วนสำคัญของการแก้ปัญหานี้เช่นกัน

### Workshop: Troubleshoot 3 สถานการณ์จำลอง

ให้วิเคราะห์ 3 สถานการณ์ต่อไปนี้โดยใช้ Flowchart (Step 605) และกรอบคิด Step 606-608 เขียนขั้นตอนการตรวจสอบและสมมติฐานที่เป็นไปได้สำหรับแต่ละสถานการณ์:

**สถานการณ์ที่ 1:** เปิดแคมเปญ Conversion ใหม่เมื่อวาน Ad Set สถานะ Active, Ad สถานะ Active, Budget ตั้งไว้ 1,500 บาท/วัน แต่ผ่านมา 18 ชั่วโมง Spend เป็น 0 บาท ไม่มี Impression เลย ให้ระบุ 5 สิ่งที่ต้องตรวจสอบตามลำดับ

**สถานการณ์ที่ 2:** แคมเปญ Lead Generation วิ่งมา 3 สัปดาห์ CPA (ต่อ Lead) อยู่ที่ 45 บาทมาตลอด สัปดาห์นี้ขยับเป็น 95 บาท CTR ลดลงจาก 2.5% เป็น 2.3% (ลดลงเล็กน้อยเท่านั้น) Frequency อยู่ที่ 2.1 (ไม่สูงผิดปกติ) แต่ Lead ที่ได้มามีคุณภาพต่ำลง (ทีม Sales รายงานว่าคนที่ทักมาไม่ค่อยสนใจซื้อจริง) ให้วิเคราะห์ว่าน่าจะเป็นสาเหตุกลุ่มไหนและตรวจสอบอย่างไรต่อ

**สถานการณ์ที่ 3:** แคมเปญ E-commerce วิ่งปกติมา 2 เดือน ROAS เฉลี่ย 3.2 แต่เดือนนี้ ROAS ตกลงเหลือ 1.1 โดย CTR และ Frequency ปกติทุกอย่างไม่เปลี่ยนแปลง (CTR 2.0% Frequency 2.4 เหมือนเดือนก่อน) ให้ตั้งสมมติฐานว่าอะไรอาจเป็นสาเหตุ (คำใบ้: ปัญหาอาจไม่ได้อยู่ที่ตัวโฆษณาเลย)

**เฉลยแนวทาง (สำหรับตรวจงานตัวเอง):**
- สถานการณ์ 1: น่าจะเป็นปัญหากลุ่ม Bid/Budget ต่ำ, Audience แคบ, หรือ Ad ยังอยู่ใน In Review — ให้เริ่มจาก Flowchart ขั้น 1-3 ก่อน
- สถานการณ์ 2: CPA สูงขึ้นแต่ CTR ไม่เปลี่ยนมาก + คุณภาพ Lead แย่ลง ชี้ไปที่ Audience ผิดกลุ่ม (ได้คนคลิกเยอะแต่ไม่ตรงเป้าหมาย) มากกว่า Fatigue — ควรตรวจ Demographic Breakdown ของ Lead ที่ได้เทียบ Lead คุณภาพดีในเดือนก่อน
- สถานการณ์ 3: เมื่อ CTR/Frequency ปกติทุกอย่างแต่ ROAS ตก ปัญหาน่าจะไม่ได้อยู่ที่โฆษณา แต่อยู่ที่ Conversion Value/Pixel Tracking (อาจมีปัญหา Tracking ที่ทำให้ Value ที่ส่งมาผิดพลาด) หรือ Checkout/Payment ฝั่งเว็บไซต์มีปัญหา — ให้ตรวจ Events Manager และทดสอบ Checkout ด้วยตัวเองเป็นอันดับแรก

### เพิ่มเติมสำหรับสถานการณ์ที่ 3: ทำไม Tracking Error ถึงเป็นสาเหตุที่ถูกมองข้ามบ่อยที่สุด

สถานการณ์ที่ 3 คือกรณีที่อันตรายที่สุดในบรรดา 3 สถานการณ์ เพราะทุก Metric ที่นักยิงแอดมองก่อนเป็นอันดับแรก (CTR, Frequency, CPM) ดูปกติหมด ทำให้คนส่วนใหญ่ไม่คิดว่าปัญหาอยู่ที่การยิงแอดเลย แต่ก็ไม่คิดไปถึง Tracking ด้วยเช่นกัน สุดท้ายจึงปล่อยผ่านไปหลายวันโดยไม่รู้ตัวว่าเงินที่เสียไปมาจาก Bug ทางเทคนิคง่าย ๆ

ตัวอย่างสาเหตุ Tracking ที่พบบ่อยในกรณีนี้:
- Currency Setting ผิดพลาดหลัง Deploy เว็บไซต์เวอร์ชันใหม่ (ส่ง Value เป็น USD แต่ Pixel ตั้งไว้อ่านเป็น THB ทำให้ Value ที่บันทึกคลาดเคลื่อนจากราคาจริงหลายเท่า)
- Promo Code/Discount ที่หักราคาไปแล้ว แต่ Purchase Event ยังส่ง Value เป็นราคาก่อนหักส่วนลด ทำให้ ROAS ที่คำนวณดูสูงกว่าความเป็นจริงในสมัยก่อน และพอแก้ Bug นี้ ROAS ที่แสดงจะดูเหมือน "ตก" ทั้งที่จริงคือค่าที่แม่นยำขึ้น
- Server-Side CAPI ส่ง Event ซ้ำกับ Browser Pixel โดยไม่มี Deduplication ที่ถูกต้อง ทำให้ระบบนับ Conversion เกินจริงในบางช่วง แล้วพอ Deduplication เริ่มทำงานถูกต้อง ตัวเลขก็ดู "ตก" ลงมาเป็นปกติ

วิธีตรวจสอบที่แนะนำ: เข้า Events Manager > Test Events ทำ Purchase ทดสอบด้วยตัวเอง (ใช้บัตรทดสอบ/โหมด Sandbox ถ้ามี) แล้วเทียบ Value ที่ Pixel บันทึกกับราคาที่จ่ายจริง หากมีความคลาดเคลื่อนแม้เพียงเล็กน้อย ให้สงสัยว่า Bug นี้อาจเกิดมานานแล้วแต่เพิ่งมาสะสมผลกระทบชัดเจนในเดือนนี้

## Workshop / แบบฝึกหัด

1. ทำ Flowchart จาก Step 605 เป็นเอกสาร 1 หน้า (Checklist แบบ Printable) ที่ทีมงานของคุณสามารถใช้ได้จริงเมื่อเจอปัญหาแคมเปญไม่วิ่ง
2. เลือกแคมเปญที่มี CPA สูงกว่าที่ต้องการในบัญชีจริง (หรือจำลองสถานการณ์) วิเคราะห์ตามกรอบ Step 606-607 แล้วเขียนแผน Isolate Variable ออกมาเป็นตาราง (ตัวแปรที่จะทดสอบ, ลำดับ, ระยะเวลา, Metric ที่จะดู)
3. ตอบ 3 สถานการณ์จำลองใน Step 610 พร้อมอธิบายเหตุผลของทุกขั้นตอนที่เลือกตรวจสอบ
4. เขียน Kill Threshold ของตัวเอง (หรือของธุรกิจที่ดูแล) เป็นลายลักษณ์อักษร: จะยอมเสียเงินทดสอบสูงสุดกี่บาทและกี่วัน ก่อนตัดสินใจ Kill โดยไม่มีข้อยกเว้น
5. เขียนแม่แบบข้อความ Escalate ของตัวเอง (ตามโครงสร้างใน Step 609) แล้วทดลองกรอกข้อมูลจากสถานการณ์ที่ 1 ในแบบฝึกหัดข้อ 3 เสมือนว่าคุณจะต้องส่งข้อความนี้ไปที่ Meta Support จริง

## สรุปและเชื่อมไปยัง Part ถัดไป

Troubleshooting ที่ดีไม่ใช่การรู้คำตอบทุกอย่างล่วงหน้า แต่คือการมีกระบวนการที่เป็นระบบสำหรับหาคำตอบอย่างมีประสิทธิภาพ Part นี้ให้คุณ 2 กรอบคิดหลัก (Flowchart สำหรับ "ไม่วิ่ง" และการวิเคราะห์ 6 กลุ่มสาเหตุสำหรับ "CPA สูง") พร้อมหลักการ Isolate Variable ที่ทำให้ทุกการแก้ปัญหาสร้าง Learning สะสมได้จริง ไม่ใช่แค่เดาแล้วลุ้น

ปัญหาที่พบบ่อยที่สุดอย่างหนึ่งที่ทำให้ Troubleshooting ยากขึ้นคือปัจจัยด้านเวลา — บางปัญหาเกิดขึ้นเพราะช่วงเวลาของปีที่มีการแข่งขันสูงขึ้นหรือ Demand เปลี่ยนไปตามฤดูกาล **Part 062 — Seasonal Campaigns และ Promotion Calendar** จะพาคุณไปวางแผนล่วงหน้าสำหรับปัจจัยเหล่านี้ เพื่อไม่ต้อง Troubleshoot แบบตั้งตัวไม่ทันเมื่อถึงช่วงเทศกาลสำคัญของปี และรู้วิธีเตรียมตัวรับมือ CPM ที่พุ่งสูงในช่วง Peak Season ก่อนที่มันจะเกิดขึ้นจริง
